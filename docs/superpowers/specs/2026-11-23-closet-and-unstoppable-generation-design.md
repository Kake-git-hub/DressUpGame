# クローゼット・止まらない生成・ホームの公開（段階 ①、v0.35.0）と、その先の順番

作者の依頼（2026-11-23）と、作者と決めたこと。この文書は、段階 ① の設計書。段階 ②〜⑥ は、決まったことだけを 9 章に残す（設計は、その段階に入るときに書く）。

前提になる文書: `2026-11-20-app-studio-portrait-sets-design.md`（8 章 = アプリの中のスタジオ。サーバーの作りと、これまでに決めたこと）。

## 1. 依頼と、なぜ作るか

作者の言葉（2026-11-23。段階 ① にかかわる分）:

- 「つくる」から、写真と色は一旦なくす。基本は、テキストのテーマで指示する。
- チケットで作ったアイテムは、別の管理画面に動かす。ホームに「あそぶ」「つくる」に加えて「クローゼット」のボタンを置き、自分が作ったアイテムが並んで編集できるようにする。
- 「つくる」でチケットを使って生成を始めたら、途中で画面を切り替えても、電源を切っても、続けて生成する。**チケットを消費したのに保存されない、が起きないようにする。**
- 自分のアイテムは、公開のアイテムより先に並べる。
- ホーム画面は、もう全員に出してよい。

質問への返事（2026-11-23）:

| 質問 | 返事 |
|---|---|
| できた服は「使う／捨てる」をなくし、自動でクローゼットに入れてよいか | よい |
| ホームを全員に出すとき、「つくる」「クローゼット」は | 販売を始めるまで、教えた端末にだけ出す。ほかの人には「あそぶ」「ともだちにおしえる」だけ |
| クローゼットの「編集」は、名前・消す・並べ替えのほかに | 既定の色（デフォルトのカラー設定） |

なぜ: チケットは、これから売る（段階 ⑥）。お金を払って作った服が、置き場所も行き先もはっきりしていて、失われないことが、売る前の土台になる。

## 2. 目標・やらないこと・起きてはいけないこと

**目標**

1. 引いたチケットは、必ず「クローゼットに入った服」か「払い戻し」のどちらかで終わる。アプリを閉じていても、端末の電源が切れていても、サーバーだけで終わりまで進む。
2. 自分の服を見る・直す場所が、クローゼットの 1 か所にまとまっている（名前・既定の色・並び順・消す）。
3. 自分の服は、ゲームのメニューで、公開の服より先に並ぶ。
4. ホーム画面が、だれにでも出る。

**やらないこと（この段階では）**

- できたことを、閉じているアプリに知らせる（プッシュ通知）。次に開いたときに分かればよい。
- クローゼットでの、位置・大きさの直し、カテゴリの移動、セットの名前の変更、セットをまとめて消す。
- 写真から顔を作る・色のテーマ（画面から外す。サーバーの写真の受け口は、そのまま残す）。
- ログイン（段階 ③）、縦画面の作り直し（段階 ②）、販売・交換・管理者の並び順（④〜⑥）。
- アプリ以外からの呼び出しを断る仕組み（App Check。販売の前に入れる）。

**起きてはいけないこと**

- チケットが減ったのに、服も払い戻しも無い。
- 同じ品目を二重に作る・二重に払い戻す（v0.27.0 で直した守りを、こわさない）。
- 「つくる」を教えていない端末が、Firebase の部品を読み込む・「つくる」「クローゼット」が見える。
- サーバーとの合わせの失敗で、端末にある自分の服が消える（いまの `sync.ts` の決まりを守る）。
- ゲームが開くまでの時間が、サーバーとの合わせを待って遅くなる。

## 3. いまの作りと、足りない所

- 生成は、アプリがサーバーの関数 `studioRun` を呼んで進める（`src/cloud/remoteBackend.ts` の `kick`）。1 回の呼び出しは、順番待ちの品目を 8 分まで作り続ける。アプリが切れたあとも、その呼び出しが動き続けるかは、確かめられていない（設計書 8.9）。8 分で終わらなかった分・途中で止まった分は、次に「つくる」を開いてアプリが呼び直すまで、進まない。
- できた服は「できた」の候補として残り、利用者が「使う」を押して初めて自分の服になる（`tools/cloud/studioCore.ts` の `keep`）。
- 分かっている穴（設計書 8.9 の「残したこと」）: チケットを引いたあと、仕事を作る前にサーバーが止まると、チケットが減ったまま。作りかけで止まった品目は、何度でも「順番待ち」に戻る（終わらないことがある）。
- できなかった品目の知らせは、仕事の全部が決まると、次に開いたときには出ない。
- 自分の服は「つくる」の画面の下に並び、できるのは「消す」だけ。メニューでは、公開の服のあとに並ぶ（`src/cloud/library.ts` の `mergeMyItems`）。
- ホーム画面は `?home=1` を開いた端末にだけ出る（`src/home/homeMode.ts`）。

## 4. 作り方の案

### 4.1 閉じても生成が進む仕組み

| 案 | 中身 | 良い点 | 悪い点 |
|---|---|---|---|
| **A. 順番待ちの列（Cloud Tasks）— 採用** | 「作る」を受けたサーバーが、仕事を列に入れる。列が、生成を進める関数を呼ぶ。失敗したら、列が間をあけて呼び直す | アプリが要らない。やり直しが付いている。1 回の持ち時間が長い（30 分まで、と理解している。計画のときに公式の文書で確かめる）。同時に進める数を列で絞れる | Cloud Tasks の API を有効にする必要がある（載せるときに自動で有効になる見込み。作者のプロジェクトでは未確認） |
| B. 仕事の文書が書かれたら動く関数 + 数分おきの見回り | Firestore の書き込みで関数が動く。止まった仕事は、時間で動く関数が拾う | 列が要らない | 持ち時間が短い（9 分）。見回りの間隔の分、待たされる。関数が 2 つ増える |
| C. いまの仕組みに、見回りだけ足す | アプリが呼ぶのは同じ。止まった仕事を、時間で動く関数が拾う | 変更が小さい | アプリを閉じたとき、いつも数分待たされる。アプリの側の段取りが残る |

作者は作り方を任せているので、こちらの判断で A にする。B・C は、持ち時間と待ち時間で劣る。

### 4.2 できた服の扱い

- **自動でクローゼットに入れる（作者の決定）。** 「使う／捨てる」をなくす。要らない服は、クローゼットで消す。
- 比べた案: 「使う／捨てる」を残し、選ばなかった候補を一定の時間で自動で入れる。選ぶ手間と、決まるまでの宙ぶらりんが残るので、やめた。

### 4.3 既定の色の持ち方

- **色スライダーの角度（-180〜180）を、服ごとにサーバーに持つ — 採用。** ゲームの色変え（`src/pipeline/recolor.ts`）をそのまま使う。絵は作り直さない。あとで端末をまたいでも同じ色になる（段階 ③）。
- 比べた案: 色を変えた絵を作り直して保存する。元の色に戻せなくなり、絵の置き場も増えるので、やめた。

## 5. 画面

### 5.1 ホーム

```
                                   v0.35.0
            きせかえ

          [   あそぶ   ]
          [   つくる   ]      ← 「つくる」を教えた端末だけ
          [ クローゼット ● ]   ← 同上。● は、新しい服がある・作っている途中
        （ともだちにおしえる）
```

- ホームは、だれにでも、開いたときに出る（`?home=1` の覚えは要らなくなる）。
- 「つくる」「クローゼット」は、「つくる」を出す端末（`src/appStudio/unlock.ts`。`?studio=1` / `?studio=fake`、あいことば）にだけ出す。ほかの端末には「あそぶ」「ともだちにおしえる」だけ。
- 右上のアカウントのボタン（中身は「じゅんびちゅう」）は、ログイン（段階 ③）ができるまで外す。*（こちらの判断。だれにでも出る画面に、使えないボタンを置かない）*
- ゲームの画面の 🏠 は、だれにでも出す。
- ゲームの画面の ✨（スタジオを開く）は外す。「つくる」の入口は、ホームの 1 つにする。*（こちらの判断。入口が 2 つあると、片方だけ保護者の確認がある、という食い違いになる。縦画面のボタンの行も 1 つ空く）*
- 保護者の確認（`AdultGate`）は、いまのホームの「つくる」と同じく、出さない（v0.32.0 の作者の指示「開発中なので確認なし」のまま）。部品は残し、1 か所の切り替えで戻せるようにする。**販売を始めるときに戻すかどうかは、段階 ⑥ の計画書で決める。**

### 5.2 つくる（大人向け。漢字かな交じり）

```
✨ 服を作る                       🎫 のこり 5 枚   ✕
ドール      [ おんなのこ ▼ ]
① 何を作る？ [ トップス ▼ ]        （セットを選ぶと、入れるものの欄が出る）
② テーマ    [ うみのおひめさま            ]
③ 絵柄      [ アニメ ▼ ]
            [ 作る（チケット 1 枚） ]

作っています…（1 分くらい）
  この画面を閉じても、アプリを閉じても、続きます。できたら、クローゼットに入ります。
┌────────┐
│ ドールが   │ あおい なみの ドレス
│ 着た絵     │ クローゼットに入りました   [ クローゼットを見る ]
└────────┘
```

- 写真（📷）と、色のテーマ（3 色）を外す。
- **ドールを選ぶ欄を足す。** *（こちらの判断。ホームから直接開くので、ゲームに行かないとドールを替えられないのは不便）* 最初に選ばれているのは、最後に遊んだドール。ゲームに出ているドールだけ。
- 「作る」を押すと、チケットが引かれ、作りかけのカードが出る。できたら、ドールが着た絵と「クローゼットに入りました」。できなかったら、理由と「チケットは戻しました」と「とじる」。
- 「自分の服」「ほかのドールの服」の欄は無くす（クローゼットへ）。利用者コードの表示は残す。
- 作りかけの仕事があるときに開くと、その続きが見える。ドールを選べるようになるので、**どのドールの仕事も出す**（カードにドールの名前を書く。いまは、開いているドールの分だけ）。

### 5.3 クローゼット（子どもも使う。ひらがな）

```
👗 クローゼット                                  ✕
[ おんなのこ ] [ おとこのこ ]          ← 自分の服のあるドール

つくっています…  ◌ トップス  ◌ くつ      ← 作りかけ（あれば）
つくれませんでした: ぼうし（チケットは もどしました）[とじる]

トップス
 ┌────┐ ┌────┐ ┌────┐
 │ NEW  │ │      │ │      │
 │ 絵   │ │ 絵   │ │ 絵   │
 └────┘ └────┘ └────┘
  なみのふく  ほしのふく  …
ボトムス
 …
```

服を押すと、その服の画面:

```
┌──────────┐  なまえ  [ なみのふく        ]
│ ドールが着た絵 │  いろ    ━━━━━●━━━━━━  [もとのいろ]
│（色は、その場で│  ならび  [◀ まえへ] [うしろへ ▶]
│  変わる）      │  セット「うみのおひめさま」
└──────────┘  [ けす ]                 [ できた ]
```

- 並ぶのは、自分の服の全部（作った服。あとの段階で、届けてもらった服・交換でもらった服も、ここに入る）。ドールごと・カテゴリごと。カテゴリの順番は、公開の素材と同じ。カテゴリの中は、ゲームのメニューと同じ順番。
- ゲームに出ていないドール（公開をやめたドール）の服も、ドールの切り替えに出して、消せるようにする（いまの「ほかのドールの服」の役目）。
- **なまえ**: 20 文字まで（いまの決まりと同じ）。
- **いろ（既定の色）**: 色スライダー。動かすと、ドールが着た絵がその場で変わる。決めた色は、メニューの絵・クローゼットの絵・着せたときの最初の色になる。「もとのいろ」で 0 に戻す。
  - 着せたあとの調整画面の色スライダーは、今までどおり使える（その服装だけの色）。調整画面の「色をもどす」は、既定の色に戻す。
  - 髪は、前髪とうしろがみの両方に同じ色。黒っぽい絵の色の付け方も、ゲームと同じ。
- **ならび**: カテゴリの中での順番を、1 つずつ動かす。*（ドラッグでの並べ替えは、作る人に任せる。◀ ▶ があれば足りる）*
- **けす**: 絵を見せて「けしますか？（もとに もどせません）」と確かめてから消す。*（こちらの判断。保護者の確認までは付けない）*
- **NEW の印**: できてから、まだ 1 回も押していない服に付く。端末ごとに覚える。ホームの「クローゼット」の ● は、NEW の服があるとき・作りかけがあるときに付く。
- 見るだけなら、つながっていなくてもよい（端末の控えから出す）。直す・消すは、つながっているときだけ（サーバーを先に変え、通ったら端末の控えを変える。通らなければ、何も変えずに知らせる）。

### 5.4 ゲームのメニュー

- カテゴリの中は、**自分の服（クローゼットの順番）→ 公開の服（素材の順番）**。自分の服どうしの最初の順番は、新しいものが先。
- 「セット」も、自分のセットが先（新しいものが先）、そのあと公開のセット。
- メニューの絵は、既定の色で出す。★ の印は、今までどおり。

## 6. サーバー

### 6.1 生成の流れ

1. **始める**（アプリが呼ぶ）: 入力を確かめ、企画を作り、**チケットを引くことと仕事を作ることを、1 つの取り引きで行う**（片方だけ、が起きない）。そのあと、仕事を列に入れる。
   - 企画（文章の AI。数秒）は、いまと同じく、チケットを引く前に行う。*（こちらの判断。企画ができなければ、チケットを引かずに、その場で理由を返せる）* 「作る」を押してから作りかけのカードが出るまでの数秒にアプリを閉じると、仕事が始まっていないことがある。その場合、チケットは減っていない。**「閉じても続く」が始まるのは、作りかけのカードが出たとき**で、画面にもそう書く（「準備中…（このまま、お待ちください）」）。
2. **進める**（列が呼ぶ。新しい関数。アプリからは呼べない）: いまの `runJob` の受け持ちの決まり（`runner` の印・30 秒おきの合図・150 秒で「止まっている」）を、そのまま使う。列は同じ仕事を 2 回呼ぶことがある前提で、二重に作らない。
   - 1 点できるごとに、**その場で自分の服として保存する**（いまの `keep` の中身）。保存できなかったら、できなかった扱い（払い戻し）。
   - 持ち時間が足りなくなったら、残りを列に入れ直して終わる。
   - 途中で落ちたら、列が間をあけて呼び直す。
   - 呼ばれたとき、ほかの呼び出しが進めている最中（合図が新しい）なら、手を出さずに、**少しあとにもう一度呼ばれるよう、列に入れ直す**（そのまま終わると、落ちた直後のやり直しが空振りになり、だれも続きを進めなくなる）。
   - 追い越された呼び出し・打ち切られた仕事（下の 5）の呼び出しは、服を残さない。同じ品目で「服ができた」と「払い戻し」の両方は起きない（服の保存にも、`runner` の印の守りを付ける）。
3. **品目ごとの回数の上限**: 1 つの品目に取りかかれるのは 3 回まで。3 回目も途中で止まったら、できなかった扱いにして、チケットを戻す（終わらない仕事を作らない）。
4. **列に頼り切らない**: 列のやり直しが尽きた・列に入れるのに失敗した、で止まった仕事は、アプリが進み具合を聞いたときに、サーバーが列に入れ直す（入れ直しは、仕事ごとに 30 秒に 1 回まで）。アプリは、もう「進める」を呼ばない。関数 `studioRun` は無くす。
5. **見回り**（1 時間に 1 回、時間で動く関数）: 終わっていない仕事を探し、止まっていれば列に入れ直す。**作ってから 24 時間たっても終わらない仕事は、残りの品目をできなかった扱いにして、チケットを戻す。** アプリを開かなくても、列がこわれていても、「服か払い戻し」で終わる。*（こちらの判断。案 B の見回りは「待たされる」のでやめたが、これは最後の守りなので、間隔は長くてよい）*
6. 前の版で「できた」のまま残っている候補は、自動で自分の服に入れる（捨てない）。
7. 検品で 2 回とも不合格だったが絵はある品目（「注意あり」）は、いまの決まりのまま: クローゼットに入り、チケットは使う。注意の内容は、「つくる」の結果のカードと、クローゼットのその服の画面に、小さく出す。*（こちらの判断。いまも「捨てる」でチケットは戻らないので、決まりは変わらない。販売の前に見直す、も前のまま）*

### 6.2 アプリが見るもの

- 進み具合（いまと同じく、数秒おきに聞く）。品目の状態は 順番待ち → 作成中 → **クローゼットに入った**（服の ID が付く）／できなかった。
- できた服の絵は、自分の服として取る（いまの「候補の絵を取る」呼び出しは要らなくなる）。
- **知らせを見たことを、サーバーが覚える。** 仕事は「終わった」あと、利用者が結果（できた・できなかった）を見るまで、開くたびに出る。見たら、もう出ない。
- 自分の服に、名前・既定の色・並び順を持たせ、変える呼び出しを足す。端末の控えを合わせるときは、足りない服を取る・消えた服を消す（いまの決まり）に加えて、**名前・色・並び順がサーバーと違えば、端末の控えを直す**（絵は取り直さない）。
- サーバーが新しい版かどうかを、最初の返事で知らせる。古いサーバーにつないだ新しいアプリは、「サーバーが古い版です（作者が載せ直す必要があります）」と出して、「作る」を押せなくする（列の無いサーバーでは、だれも生成を進めないため）。

### 6.3 アプリを開いたとき

- この端末で「つくる」か「クローゼット」を 1 回でも使った（利用者ができている）なら、画面が出たあとに、裏でサーバーにつなぎ、自分の服を合わせ、作りかけの仕事を見る。ゲームの起動は待たせない。
- 作りかけの仕事がある間は、ときどき聞き直す（「つくる」「クローゼット」を開いている間は数秒おき。ほかは 30 秒おき。アプリに戻ってきたときは、すぐ）。新しい服が届いたら、メニューに足し、ホームに ● を付ける。
- 「つくる」を教えていない端末は、Firebase の部品を読み込まない（今までどおり）。

### 6.4 費用と上限

- 1 日の画像の上限（サーバー全体・利用者ごと）は、そのまま。列で、同時に進める仕事を 3 つまでに絞る（いまの `studioRun` の同時数と同じ）。
- Cloud Tasks の代金は、この規模では 0 円の見込み（月 100 万回まで無料、と調べた。2026-11-23）。

### 6.5 利用者が増えたとき（作者の質問、2026-11-23）

同時 3 つ・1 点 30 秒〜1 分だと、さばけるのは 1 時間に 180 点ほど。100 人が同時に 1 点ずつ頼むと、最後の人は 30 分ほど待つ。その前に、1 日の上限（既定 100 枚）に当たる。

- **この段階で入れる**: 同時に進める数を、コードの 1 か所の設定値にする（数字を変えて載せ直すだけで増やせる）。順番待ちのまま 1 分たった品目には、「こみあっています。できたら、クローゼットに入ります」と出す（止まったと思われないように）。
- **販売の段階（⑥）で考える**: セットのパーツを並行して作る、「あと何人待ち」を出す。本当の天井は Gemini の側の 1 分あたりの枚数の制限（課金の段階で決まる。作者のキーでの値は未確認）なので、そのころに実測してから決める。

## 7. 確かめ方

- サーバーの本体（`tools/cloud/`）は、今までどおり、メモリの中の置き場と偽の AI で、テストを先に書く。足すテスト: 引くのと仕事を作るのが片方だけにならない／できたら自動で服になる／3 回で打ち切って払い戻す／列が 2 回呼んでも 1 回しか作らない／止まった仕事を、聞かれたときに入れ直す（30 秒に 1 回まで）／前の版の「できた」が服になる／見た知らせは出ない。
- エミュレーター（`npm run firebase:test`）: 列の関数が、エミュレーターで動くかを計画のときに確かめる（`firebase.json` と、テストの起動の `--only` に、列のエミュレーターを足す必要がある見込み）。動かなければ、列の関数の中身を直接呼んで確かめる。**エミュレーターは、本物の権限・やり直しの間隔・持ち時間をまねない**ので、列そのものは、作者のプロジェクトでの確認項目にする。
- 本物で外れやすい所（計画のときに、公式の文書で確かめる）: 東京の関数を列に入れるときは、関数の場所まで含めた名前で指定する。列に入れる側の関数に、列に入れる権限が要る。ここを外すと、生成が 1 つも始まらない。
- 画面は E2E（偽の裏側 `fakeBackend.ts`。本物と同じ形に直す）: ホームがだれにでも出る・教えていない端末に「つくる」「クローゼット」が無い／作る → 読み込み直す（閉じたつもり）→ クローゼットに入っている／名前・色・並び・消す／メニューで自分の服が先・既定の色で出る／できなかった知らせは 1 回だけ。
- いまある E2E（`dressup.spec.ts` など）は、ホームを通るようになる。直し方（「あそぶ」を押す・テスト用の開け方）は、作る人に任せる。

**作者に確かめてもらうこと（こちらでは確かめられない）**

- `npm run firebase:deploy` が、列の関数と見回りの関数を含めて通るか（API を有効にするか聞かれたら「はい」。古い関数 `studioRun` を消すか聞かれたら「はい」）。載せたあと、1 点作って、1〜2 分でクローゼットに入るか。**入らなければ、`npm run firebase:logs` の文字をもらう**（権限の不足は、ここに出る）。
- 本物で: 「作る」を押してすぐアプリを閉じ、1〜2 分後に開いて、クローゼットに入っているか。セット（3 点くらい）でも同じか。
- iPad のホーム画面のアプリで、ホーム・クローゼットの見え方と手ざわり。

## 8. 作る人に任せること

- Firestore の文書の形（服の名前・色・並び順・更新の印、仕事の「見た」の印、列に入れた時刻）、関数の名前と分け方、列の設定の細かい値（やり直しの回数と間隔）。
- アプリとサーバーの呼び出しの形（`src/cloud/backend.ts`・`wire.ts`）。「使う」「捨てる」「候補の絵」は無くしてよい。
- クローゼットの見た目の細部（絵の大きさ、色、並べ替えをドラッグでもできるようにするか）。画面は、ホームと同じく、押したときに読み込む。
- メニューの絵を既定の色にするやり方（重ねるときに色を付けた絵を作って覚える、など。起動を遅くしないこと）。
- テスト用にホームを飛ばす開け方を残すかどうか。
- 写真の画面の部品とテストは消してよい（サーバーの受け口と、そのテストは残す）。
- 版数（`src/version.ts`・`README.md` を v0.35.0 に）、`docs/firebase-setup.md`（載せ直しの手順に、列のことを足す）、`docs/superpowers/HANDOFF.md`（v0.28.0 のまま止まっているので、いまの状態に直す）。
