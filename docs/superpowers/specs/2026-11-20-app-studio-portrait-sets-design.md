# アプリ内スタジオ・縦画面・セット・重なりのドラッグ（設計、2026-11-20）

作者の依頼（2026-11-20）と、話し合って決めたことの記録。実装の前に作者の了承を得る。
段階ごとの実装計画は `docs/superpowers/plans/` に、段階を始めるときに書く（前の段階が終わった時点のコードをもとに書く。ロードマップと同じやり方）。

## 1. 依頼と、なぜ作るか

作者は、このゲームを「利用者が自分でチケット（有料）を使って服を作れるアプリ」にしたい。
作った服はその利用者にだけ見える。将来は、自分の顔をアニメ化して着せ替えの品目にもしたい。
そのために、いまは PC でしか動かないスタジオを、アプリの中から、子どもや保護者でも迷わず使える形にする。
あわせて、遊ぶ画面を使いやすくする（縦画面、iPad の上のバーとの重なり、重なりの並べ替え、セット）。

依頼は次の 7 つ。別々の仕事として、この順に 1 つずつ公開する。

| 段階 | 版 | 内容 |
|---|---|---|
| A | v0.22.0 | 小さな直し: 絵柄「マンガ」、横画面の PWA で iPad の上のバーに重ならない、下の「ドラッグして…」を消す、版数を右上に小さく |
| B | v0.23.0 | 調整画面の重なりを、ドラッグで並べ替える |
| C | v0.24.0 | 縦画面（メニュー類は下） |
| D | v0.25.0 | セット: 同じテーマで複数パーツを一括で作り、セットを選ぶと全パーツが一度に着く |
| E | v0.26.0〜 | アプリ内スタジオ（Firebase）。チケットの残り・自分だけの服・作者が特定の利用者に届ける |
| F | 計画だけ | チケットの販売、アカウントの引き継ぎ、顔のアニメ化 |

作者が決めたこと:

- サーバーは **Firebase**。生成も画像の処理も Firebase 側で行う（下の 3 章の案 1）。有料プラン（Blaze）への切り替えを前提にする。
- 「服ごとに、見える利用者を限る」は、いまは作らない。**サーバーができたら、サーバー側で対応する**（段階 E の最後）。
- セットは、**ばらばらのパーツ**として扱う。要らないパーツは 1 点ずつ消せる。

## 2. 目標・やらないこと・起きてはいけないこと

**目標**

- スタジオを使わない人の遊び方・速さ・オフラインでの動作は、いまと変わらない。
- 縦でも横でも遊べる。持ち替えても、着ている服の位置がずれない。
- アプリから「何を作るか・テーマ・絵柄」の 3 つを選ぶだけで、服が 1 点できて、自分のメニューに入る。
- 画像生成のキー（Gemini）は、端末に渡さない。チケットの残りは、サーバーだけが増減する。

**やらないこと（今回）**

- チケットの販売・決済、Google や Apple でのログイン、顔のアニメ化（段階 F。計画だけ）。
- アプリから、全員に見える素材を公開すること（公開は、今までどおり PC のスタジオから）。
- アプリでの手直し（位置の微調整・消しゴム・復元）、ドールや背景をアプリから作ること。
- 公開の置き場にある服を、利用者ごとに隠すこと（公開の置き場の絵は、場所を知っていれば見えるため、隠すだけの仕組みは作らない）。
- 描画の Canvas 2D への置き換え、タップで着脱（ロードマップの残り。今回は触らない）。

**起きてはいけないこと**

- スタジオを使わない人の、最初の読み込みが重くなる（Firebase の部品は、使うときにだけ読む）。
- いま保存されている服装が、更新のあと崩れる・消える。
- 横画面の見た目や操作が、縦画面の対応で悪くなる。
- 端末の操作だけで、チケットの残りを増やせる。ほかの利用者の服が見える。
- 生成に失敗したのに、チケットが減ったままになる。

## 3. 作り方の案（段階 E の土台）

| 案 | 内容 | 良い点 | 困る点 | 結果 |
|---|---|---|---|---|
| 1. 生成も画像の処理も Firebase 側 | いまの PC スタジオの「作る中身」（企画・画像生成・切り抜き・位置合わせ。`tools/studio/generate.ts` と品目ごとの処理、sharp）を、そのままサーバーの関数に載せる。アプリは「テーマを送る → できた絵を受け取る」だけ | 作る中身は書き直さない。テスト済みの処理を使える。iPad が重くならない。PC のスタジオと同じ絵になる | 1 回の生成ごとにサーバーが数十秒動く（無料枠内の見込み）。まわりの部分は、サーバー用に作り直す（下の注） | **採用**（作者の決定） |
| 2. Firebase は中継とチケットだけ、処理は端末の中 | 切り抜きや位置合わせを端末で行う | サーバーが軽い | 画像の読み書き（sharp の部分）を書き直す。端末での速さとメモリが未知。PC のスタジオと二重になる | 不採用 |
| 3. アプリから Gemini を直接呼ぶ（Firebase AI Logic） | サーバーの関数なし | いちばん簡単。無料プランでも動く | 利用者ごとのチケット残数で止められない（全員一律の回数制限だけ） | 不採用 |

注（案 1 で、サーバー用に作り直す部分）: 生成の進み具合の置き場（いまは PC のメモリの中。`tools/studio/api.ts`）、画像の枚数の上限の記録（いまは PC のファイル。`tools/studio/budget.ts`）、保存先（いまは PC のフォルダと git）。この 3 つは Firestore と Storage に置き換える。「手足の先を服に合わせる」と位置の微調整は、いまは PC の画面の中で計算している（`src/studio/ItemCard.tsx`）ので、アプリの最初の版には載せない（くつ・てぶくろの「隠す所」は、サーバーの処理が作るので、そのまま使える）。

その前に比べた案（2026-11-20 の話し合い）: 「サーバー無しで、作者の端末にキーを入力する」案は、以前の決定「キーは画面に入力しない」と逆で、ほかの人が使えず、将来は捨てる部分が出るので、不採用。

Firebase について確かめたこと（公式の説明、2026-11-20）:

- サーバー側の処理（Cloud Functions）と画像の置き場（Cloud Storage）は、どちらも Blaze（従量制、クレジットカードの登録が必要）でしか使えない。
- Blaze でも無料枠がある（関数は月 200 万回の呼び出し・40 万 GB 秒まで）。使い始めの規模なら Firebase 自体はほぼ 0 円の見込み。かかるのは、今までどおり Gemini の画像代。
- 使いすぎに備えて、最初に「予算の知らせ」を設定する。

## 4. 段階 A: 小さな直し（v0.22.0）

1. **絵柄「マンガ」**: `src/studio/stylePresets.ts` に 1 つ足す。ペンの線（強弱あり）とトーン風の影、色は付ける（白黒にすると、色のあるドールから浮くため。これは、こちらの判断）。
2. **iPad の上のバーとの重なり**: 画面の上の「あけておく高さ」を 1 つの値（CSS の変数）にまとめ、メニュー・ボタン・版数・調整画面のすべてがそれを使う。ホーム画面から開いたとき（PWA）は、端末が教える高さと 24px の大きいほうをあける。
   - 何がどう重なっているかは、こちらでは見えていない。**作者の画面の写真をもらってから直す**（時計や電池の表示との重なりか、iPadOS の窓のボタンとの重なりかで、あける場所が変わる）。写真が無いまま進めるときは、上の決まり（24px 以上あける）だけを入れて公開し、直ったかを確認項目として作者に渡す。
3. **下の「ドラッグしてドールにきせてね！」**を消す（`app-footer`）。空いた分、メニューが下に伸びる。
4. **版数**: 右上に小さく（`.version-badge` の名前は残す。公開サイトの確認が使っている）。調整中も出す。

## 5. 段階 B: 重なりをドラッグで並べ替える（v0.23.0）

いまは、調整画面の左の一覧（上が手前。まんなかにドール）で、調整中の 1 点を ▲▼ で動かす。

- 一覧の絵を**つかんで上下に動かす**と、その位置に入る。調整中の服だけでなく、どの服でも動かせる。ドールの行より下へ動かすと、ドールの後ろに回る。ドールの行は動かせない。
- 軽く押す（動かさない）と、今までどおり、その服の調整に切り替わる。
- 動かしている間、ほかの絵は場所をあける。離した時点で、キャンバスにその場で反映する。
- ▲▼ ボタンは残す（細かい 1 つ分の移動に使える）。
- 髪は今までどおり、前髪とうしろがみが別々の行（重なりだけは 1 枚ずつ）。
- 重なりの値の計算は `src/engine/layers.ts` に「この服を、一覧のこの位置に入れたときの値」を返す関数として足す（いまの `moveLayer` と同じ考え方で、となりの値の中間に置く）。

## 6. 段階 C: 縦画面（v0.24.0）

v0.10.0 で縦をやめ、縦に持つと「よこにしてね」を出している。これを、縦でも遊べるようにする。

**対象**: iPad の縦と、スマホの縦（幅 360px から）。スマホの横は、いまの横画面がそのまま出る（専用の調整はしない）。これは、こちらの判断（利用者が増えるなら、スマホで開く人が多いと考えた）。

**画面の配置（縦）**

```
┌────────────────────────┐
│（上のバーの分をあける）  v0.24.0 │
│                                │
│        背景（正方形）            │
│          ドール                 │
│                                │
├────────────────────────┤
│ [ドール▼][🖼はいけい][かお][トップス][くつ]…   →  │ ← カテゴリ（横に流す）
│ [服] [服] [服] [服] [服] …                  →  │ ← 選んだカテゴリの服（横に流す）
│  👗ちょうせい   📷しゃしん   ✨つくる   🔄リセット  │ ← ボタン
└────────────────────────┘
```

- 背景の正方形は、「画面の幅」と「メニューを除いた高さ」の小さいほうに合わせ、上に置く。
- カテゴリの行はいつも出ている（横画面のような「もどる」は要らない）。服は、**上へ**ドラッグしてドールに着せる（一覧は横に流すので、指の向きで見分けられる）。
- 縦に余裕がある端末（スマホ）では、服の行を 2 段にする。
- 調整画面も、重なりの一覧と色・元に戻す・おわりのボタンを下に置く。
- 「よこにしてね」の案内と、PWA の「横向き固定」の設定をやめる。

**持ち替えても位置がずれないようにする**（この段階でいちばん大きい変更）

いまは、服の位置の調整値を「画面の px」で持っている。縦と横で 1px の意味が変わるので、持ち替えると服がずれる。

- 調整値を「ドールの絵の px」（ドールのキャンバスでの長さ）で持つように変える。描くとき・調整画面で、画面の縮尺を掛ける。
- いま保存されている服装は、最初に読むときに 1 回だけ変換する（保存の形に版の印を付ける）。いまの保存は横画面で作られたものなので、**横にしたときの縮尺**（画面の長いほうを幅、短いほうを高さとして計算した値）で変換する。更新のあと最初に縦で開いても、同じ結果になる。
- 描画側の「左のメニューの幅・右のボタンの幅」という決め打ちを、「ドールを描いてよい四角（位置と大きさ）」に置き換える。横画面は、いまと同じ数値になるようにする（見た目を変えない）。

## 7. 段階 D: セット（v0.25.0）

**考え方**: セットは「同じテーマで一度に作った、ふつうの服の集まり」。パーツは 1 点ずつ各カテゴリに入り、1 点ずつ着られ、1 点ずつ消せる。

**素材の一覧（`manifest.json`）**

- ドールに `sets`（`{ id, name }` の並び）、服に `set`（セットの ID）を足す。どちらも省略できる。古い版のアプリは、知らない項目を読み飛ばすので、そのまま動く。
- パーツが 1 点も残っていないセットは、一覧から消す。

**スタジオ（PC。段階 E でアプリにも同じものが載る）**

- 「テーマから作る」の「作るもの」に「セット」を足す。選ぶと、入れるカテゴリにチェックを付ける欄が出る（最初は、かお・うしろがみ以外の全部。選んだ内容はドールごとに覚える）。
- 企画（文章の AI）に、「選んだカテゴリごとに 1 点、同じ色の組み合わせと飾りでそろえた 1 組」を作らせる。セットの名前も決めさせる。
- **文章の AI を Gemini でも動かせるようにする**（この段階で入れる）。いまの「テーマから作る」は、Claude のキーと Gemini のキーの両方が無いと押せない。Claude のキーが無いときは、Gemini の文章のモデルで企画と検品を行う（Gemini のキーだけで「テーマから作る」が使える）。Claude のキーがあれば、今までどおり Claude を使う。段階 E のサーバーも、同じ部品を使う。
- 画像は、今までどおり 1 点ずつ作る（髪・くつ・顔は、それぞれの専用の作り方のまま）。**6 パーツのセットなら、画像は 6〜12 枚**（作り直しを含む）。
- できた候補は 1 点ずつ確かめて保存する（保存しなかったパーツは、セットに入らない）。「ぜんぶ保存」も付ける。
- 「一覧」で、服にセットの名前を出す。服を消す・セットから外す・セットの名前を変える、ができる。

**ゲーム**

- セットが 1 つでもあるドールでは、メニューの先頭にカテゴリ「セット」が出る。
- セットの絵は、パーツのサムネイルを 4 つまで並べたもの（専用の絵は持たない。パーツを消しても、絵が古くならない）。
- セットをドールに着せると、残っているパーツが全部、一度に着く（1 点ずつ着せたのと同じ結果。同じカテゴリの服は入れ替わる）。光るのと音は 1 回。
- パーツが 1 点だけになったセットも、そのまま出す。

## 8. 段階 E: アプリ内スタジオ（v0.26.0〜）

### 8.1 Firebase の使い方

| 部品 | 使い道 |
|---|---|
| Authentication | 利用者の見分け。最初は「自動（匿名）」。何も入力しない。スタジオを初めて開いたときに作る |
| Cloud Functions（2 世代、Node、東京） | 企画・画像生成・切り抜き・位置合わせ・保存。Gemini のキーは、ここの「秘密の値」に置く |
| Firestore | 利用者（チケットの残り・利用者コード）、生成の進み具合、自分の服の一覧、チケットの増減の記録 |
| Cloud Storage | 自分の服の絵（その利用者だけが読める）、生成中の候補の絵 |

- ゲームの本体は、今までどおり GitHub Pages に置く。公開の素材も、今までどおり素材リポジトリから配る。
- 端末からの書き込みは、すべて関数を通す。端末から直接できるのは、自分の分を読むことだけ（Firestore と Storage の決まりで守る）。
- 文章の AI（企画と検品）は、アプリでは Gemini の文章のモデルを使う（段階 D で作る部品）。
- サーバーの関数は、`functions/` に置き、`tools/studio/` と `src/pipeline/` の処理を取り込んで 1 つにまとめてから載せる。ドールの絵と型紙は、公開されている素材（`manifest.json`、`files/`、`studio/templates.json`、`studio/masters/`）から読む。公開されている型紙は「アニメ」の分だけ、2 倍の元画像は 4 体のうち 2 体の分だけなので、無いものは、いまの PC と同じく、ドールの絵から推定する・拡大して作る。
- **作れるドール**: ゲームに出ているドールなら、どれでも作れる。自分の服は「ドールの ID・カテゴリの ID」を覚えている。公開の素材からそのドールやカテゴリが無くなると、その服はメニューに出なくなる（消しはしない）。販売を始めたあとは、「利用者の服があるドールは、消さない・形を変えない」を運用の決まりにする。作者が進めている「アニメ」を消す件は、段階 E を開ける前に済ませる。

### 8.2 チケット

- **1 点 = 1 枚**。セットは、パーツの数だけ使う（6 パーツ = 6 枚）。作る前に、何枚使うかを画面に出す。
- 絵が 1 枚もできなかった品目（失敗）の分は、チケットを戻す。できたが気に入らない、は戻さない（内部で検品して、不合格なら 1 回だけ自動で作り直す。いまの PC と同じ）。検品で 2 回とも不合格だったが絵はある品目（「注意あり」）は、注意の内容を出したうえで、いまはチケットを使ったものとして扱う（作者が配っている間の決まり。販売の前に見直す）。
- **開ける前に、出来を測る**: アプリには、人の目での検品も手直しも無い。Gemini の文章のモデルでの検品は、まだ本物で試していない（これまでの本物の生成は、検品なし・1 回だけで回した）。段階 E の中で、10 点ほどを本物で作り、「そのまま使える割合」を作者に報告してから、利用者に開ける。
- 新しい利用者の残りは 0 枚。**いまは、作者が手で配る**（下の「作者の画面」）。販売は段階 F。
- 作者（管理者）は、枚数の制限なし（記録は残す）。1 日の画像の上限（いまの PC と同じ考え方）は、サーバー全体にも付ける。
- 利用者には、短い「利用者コード」（8 文字ほど）を出す。作者に伝えると、チケットや服を届けてもらえる。

### 8.3 アプリの画面

右下（縦では下）のボタンに「✨つくる」を足す。開くと、画面いっぱいのスタジオが出る。
販売を始めるまでは、**「✨つくる」は、ふだんは出さない**（公開サイトを開いた知らない人に、使えないボタンを見せない）。作者が教えた開け方（専用の URL を 1 回開く）をした端末にだけ出て、そのあとは覚えている。

```
✨ つくる                 のこり 🎫 5 まい   ✕
① なにを つくる？  [トップス][ボトムス][ドレス][くつ][かみ]…[セット]
② テーマ          [ うみの おひめさま                    ]
③ えがら          [アニメ][マンガ][リアル][ゆめかわ][えほん][ポップ]
            [ つくる（チケット 1 まい） ]

つくっています…（1 ぷんくらい）
┌────────┐
│ ドールが   │  あおい なみの ドレス
│ 着た絵     │  [ つかう ]  [ すてる ]
└────────┘
```

- いま遊んでいるドールの服を作る。カテゴリは、そのドールのカテゴリから選ぶ。
- できた絵は、ドールが着た姿で見せる。「つかう」で自分の服に入り、メニューに出る。「すてる」で消える。
- 作っている間にアプリを閉じても、次に開いたときに続きが見られる。
- 「じぶんのふく」の一覧で、作った服を消せる。
- インターネットにつながっていないと、スタジオは開けない（ゲームは遊べる）。

### 8.4 自分の服を、ゲームに出す

- 自分の服は、公開の服と同じメニュー・同じカテゴリに並ぶ（小さな印を付ける）。
- 絵は端末の中にも控えを持つ（オフラインでも着られる）。ゲームを開くときは、Firebase の部品を読まずに、端末の控えから出す。つながっているときに、裏でサーバーと合わせる（足りない絵を取る、消した服を消す）。
- 一度もスタジオを使っていない端末では、Firebase の部品を読まない。
- 自分の服の ID は、公開の服と重ならない形にする。着ている服の保存・復元は、今までと同じ仕組みで動く。

### 8.5 作者の画面（管理者）

- 管理者の印は、Firebase の管理画面で作者の利用者に付ける。
- アプリのスタジオに、管理者にだけ出る欄を足す: 利用者コードを入れて、(1) チケットを配る、(2) **自分の服の中から選んだ服を、その利用者に届ける**（その利用者の「自分の服」に入る。ほかの人には見えない）。
- (2) が、「服ごとに、見える利用者を限る」の答え。絵は、その利用者だけが読める置き場に入るので、隠すだけではなく、本当に見えない。

### 8.6 分かっている弱点と、まだ決まっていないこと

- **Gemini の利用の決まり（年齢）**: Gemini API の決まりには、「18 歳未満に向けた、または 18 歳未満が使いそうなアプリの一部として、この API を使ってはいけない」とある（Google Cloud 側の生成 AI の決まりにも、同じ文がある。2026-11-20 に公式の文面で確かめた）。子ども向けのゲームの中で、利用者が自分で生成を動かす機能は、これに当たるおそれがある。どこまでが当たるかの公式の説明は見つかっていない（「大人だけが使う画面に分ければよいか」という開発者の質問に、Google は答えていない）。法律や契約の判断は、こちらではできない。考えられる道は 3 つ:
  1. 「つくる」を、保護者（大人）が使う画面として、子どもの遊ぶ画面から分ける（入口で大人であることを確かめる）。販売のときの「保護者の確認」と同じ入口にできる。決まりを満たすかは、Google への問い合わせか専門家の確認が要る。
  2. 画像の AI を、決まりが合う別の会社のものに替える。いまの作り方（マネキンの絵に服を描かせる）がその AI でできるかを、試し直す必要がある。
  3. 利用者は頼むだけで、生成は作者（大人）が行う。
  段階 A〜D には関係しない。**段階 E を始める前に、作者と決める。**
- **PC のスタジオで作った服を、特定の利用者に届けるか**: 8.5 は、アプリで作った服だけを届けられる。PC で手直しした服も届けたいなら、PC のスタジオから Firebase に上げる道（PC のスタジオが、管理者として Firebase に入る）を足す。作者に確認する。

- 匿名の利用者は、アプリのデータを消す・ホーム画面のアプリを消すと、別の利用者になる（チケットと服を引き継げない）。Safari で開いたときと、ホーム画面から開いたときも、別の利用者になる。販売を始める前に、Google か Apple との結び付け（段階 F）が要る。それまでは、作者が配り直せる。
- 利用者が自由に書くテーマは、いまの決まり（キャラクター名などを書かせない、断られたら書き直す）と、文字数の上限（60 文字）で受ける。

### 8.7 作者に用意してもらうもの

1. Firebase のプロジェクトを作り、Blaze に切り替える。予算の知らせを設定する。
2. Authentication（匿名）、Firestore、Storage を有効にする（場所は東京）。
3. Gemini のキーを、関数の「秘密の値」に入れる。
4. GitHub から自動で載せるための鍵（サービスアカウント）を作り、リポジトリの Secrets に入れる。

手順は、段階 E の最初に、画面の写真つきの手順書にして渡す。アプリに書く Firebase の設定値（`apiKey` など）は、公開してよい値（Gemini のキーとは別物）。

### 8.8 確かめ方

- 関数の中身は、今までどおり「偽の AI」を差し込むテストで確かめる。チケットの増減・戻し・決まり（ほかの人の分が読めない）は、Firebase のエミュレーター（手元で動く模型）で確かめる。エミュレーターがクラウドの作業環境で動かないときは、同じ内容を偽物で確かめ、作者のプロジェクトでの確認項目として渡す。
- 画面は E2E（偽のサーバー）で確かめる。本物の生成は、作者のプロジェクトができてから、枚数を報告しながら少数だけ行う。

## 10. 進め方

- 段階ごとに、計画 → テストを先に → 実装 → 別の目の全体レビュー → 版数（`src/version.ts` と `README.md`）→ 作者の iPad での確認項目、の順。
- `main` へのマージ（= 公開）は、段階ごとに作者に確かめてから。
- 段階 A〜D は Firebase が無くても進められる。作者の Firebase の用意（8.7）は、その間に進めてもらえる。
- 画像生成を使うのは、段階 D の確認（セットを 1 組）と、段階 E の確認（数点）。そのつど枚数を報告する。

## 11. 実装する人に任せること

- 縦画面の細かい大きさ（ボタンや行の高さ）、ドラッグの手ざわり（動き始めの遊び、端での自動スクロール）。
- 重なりの値の決め方の細部、保存の形の版の付け方。
- Firestore の文書の形、関数の分け方（始める・進める・保存する）、途中で止まった生成の扱い（やり直せること、チケットが減ったままにならないこと、を満たせばよい）。
- 端末の控えの持ち方（旧方式の片付け `src/content/legacyCleanup.ts` が消すデータベースとは、別の名前にすること）。
- セットの ID の付け方、セットの絵の並べ方。
