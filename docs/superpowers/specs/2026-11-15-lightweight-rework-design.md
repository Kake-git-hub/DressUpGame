# きせかえゲーム 軽量化・操作性・素材準備の改善 設計書

- 作成日: 2026-11-15
- 対象: v0.9.6（コミット `cbb39f0`）
- 状態: **レビュー待ち（未承認）**

## 1. ねらい

今の遊び（ドールを選ぶ → カテゴリから服を選んで着せる → 位置・大きさ・傾き・色を調整 → 背景を変える → 写真を撮る）は変えずに、次の3つを達成する。

1. **軽量さ**: 読み込むプログラム、保存容量、メモリ、操作中の処理を減らす。
2. **操作性の良さ**: 子どもが iPad で迷わず・待たずに遊べる。
3. **画像素材の準備の容易さ**: 「ドールと同じキャンバスに描いた PNG をフォルダに入れるだけ」で済むようにする。

## 2. 現状レビュー（実測）

計測条件: 本番ビルドを Chromium（1180×820、ソフトウェア描画）で起動し、`preset-original/preset-template/doll-アニメ`（ドール1・服81・背景20、ZIP 61MB）を取り込んで操作した。ソフトウェア描画なので時間の絶対値は実機より遅いが、回数とバイト数は環境に依存しない。

| 項目 | 現状 |
|---|---|
| JS 合計（minify 後） | 約 922 KB（gzip 約 272 KB）。内訳: PixiJS 525 KB / React 193 KB / JSZip ほか 111 KB / アプリ本体 94 KB |
| PWA の事前キャッシュ | 3.8 MB。うち未使用のドール画像 2 枚で 2.1 MB、アイコン 1 枚で 755 KB |
| 取り込み後の保存容量（IndexedDB） | 83 MB。全画像を base64 文字列で保存（204 レコード） |
| 起動直後の JS ヒープ | 92 MB。全ドール・全服・全背景の画像を文字列のまま全部メモリに載せる |
| 服を1枚着た状態で、別の服を 40 回ぶんドラッグ | 服全体の再描画が 39 回、localStorage への書き込みが 40 回・計 40.5 MB |
| 着ている服の保存データ | 8 枚で 2.07 MB（画像そのものを含む）。localStorage の上限は約 5 MB |
| ZIP の取り込み時間 | 約 9 秒（再取り込みでも毎回すべて処理し直す） |

### 2.1 軽さの問題

- **ドラッグ中の無駄な再描画（最大の問題）**。`useDressUp.getEquippedItems()` が呼ばれるたびに新しい配列を返すため（`src/hooks/useDressUp.ts:129`）、`App` が再レンダリングされるたびに「着ている服が変わった」と判定される。ドラッグ中は指が動くたびに `App` が再レンダリングされるので（`src/App.tsx:429` の `setDraggingPreview`）、毎回、服の全スプライト作り直し＋テクスチャ焼き込み（`src/engine/PixiEngine.ts:411-563`）と、着ている服の保存（`src/App.tsx:286`）が走る。
- **保存データに画像本体が入っている**。着ている服の保存（`src/services/stateStorage.ts:40`）がアイテムを丸ごと JSON 化しており、画像の data URL が含まれる。大きい服が数枚重なると上限を超え、保存が黙って失敗する（`catch` でログのみ）。
- **画像を base64 文字列で持っている**。保存容量が約 1.33 倍になり、メモリ上ではさらに膨らむ。起動時に全ドール分を逐次読み込む（`src/App.tsx:206-228`、`src/services/assetStorage.ts:469-528`）。
- **PixiJS が JS の 57% を占める**。このゲームが描くのは「静止画を十数枚、位置・拡大・回転・色相を付けて重ねる」だけで、毎フレームの描画もアニメーションもない。現在は Ticker を1秒後に止める、`cacheAsTexture` で焼き込む、といった「Pixi を止めるための工夫」が入っている。
- **使われていないコードが約 1/3**。`App` から到達できないもの: `AIFaceGenerator` `CategorySelector` `ClothingItem` `ClothingPalette` `DollControlPanel` `DraggableClothingItem` `ItemImporter` `ItemManager` `ChromaKeyFilter` `EdgeTrimFilter` `aiGenerator` `dataManager`、および `assetStorage.ts` 内の約 510 行。`DrawingCanvas` `EraserCanvas` は描画されているが、有効にする手段がない。合計およそ 3,900 行（全体は約 12,000 行）。
- **リポジトリ**。`.gitignore` に入っている `preset-original/`（94 MB）と `*.png~` バックアップ 14 個が追跡されている。

### 2.2 操作性の問題

- **横画面ではタップしても着られない**（実測: タップ後の装備数 0）。10px 以上ドラッグしてメニューの外で離す必要がある（`src/components/DressUpMenu.tsx:546-558`）。縦画面は逆にタップのみ。
- **アイテム一覧は、サムネイルの上ではスクロールできない**。サムネイル全体が `touch-action: none` のため、右側 30px の余白でしかスクロールできない（`DressUpMenu.tsx:570, 717`）。
- **着せるたび・脱がせるたびにカテゴリ一覧へ戻される**（縦画面の着用時、両画面の「なし」）。同じカテゴリで何着も試しにくい。
- **調整できるのは「最後に着せた1枚」だけ**（`src/App.tsx:344`）。前に着せた服を直すには着せ直す必要がある。**ドールの移動・拡大は、服を全部脱がせないとできない**（`src/App.tsx:337`）。
- **調整した位置が画面サイズに依存する**。調整量を画面ピクセルで保存しているため（`PixiEngine.ts:471`）、画面の向きや端末が変わると服がずれる（実測: 横画面で動かしたドレスが縦画面で大きくずれた）。ドールを拡大縮小しても調整量は追従しない。
- **調整プレビューが別実装**。調整中は Pixi ではなく CSS の `<img>` でプレビューしている（`src/components/ItemAdjustPanel.tsx:544-615`）。2つの描画の位置合わせが難しく、直近 30 コミットのうち 12 件がこのずれの修正。
- **画面を横→縦に変えるとドールが消える**（実測。再読み込みで復帰。実機での確認が必要）。
- README に「WebGL コンテキストロストが稀に発生」と既知の問題として記載あり。

### 2.3 素材準備の問題

- **サムネイルが実質手作り**。自動サムネイルはキャンバス全体を 128px に縮めるだけなので（`assetStorage.ts:125-160`）、靴や帽子は豆粒になる。サンプルでは 91 点中 84 点に手作りの `_サムネ` 画像がある。
- **緑背景は自動で抜けない**。README は「グリーンバック自動透過」と書いているが、描画時のフィルタは削除済み（`PixiEngine.ts:815-830` は空のメソッド）、取り込み時にも実行されない。サンプルの 4 点（ショートパンツ、ロングスカート、赤いチェックのスカート、ショートヘア）は不透明な緑背景のまま。
- **右下 160px を無条件に消す**（透かし除去、`assetStorage.ts:193-221`）。右下まで描かれた素材は欠ける。幅 495px の画像では幅の 1/3 が対象になる。
- **命名ルールが2系統あり、書類と食い違う**。フォルダ方式（`04_5_トップス/名前.png`）とファイル名方式（`4_5_トップス_名前_ID.png`）があり、後者はどの書類にも書かれていない。ファイル名方式では、末尾の英数字が ID 扱いになって名前が欠ける、`movable` を指定できない、などの癖がある。README の例 `04_1.5_ドレス` は小数を解釈できず、意図どおりに動かない。
- **説明書が 5 つあり互いに矛盾する**（`README.md`、`docs/AI_GENERATION_GUIDE.md`、`preset-template/README.txt`、`AI_PROMPT_GUIDE.txt`、`着せ替えアイテムプロンプト例.txt`）。推奨サイズが 512×1024 / 800〜1200px / 1024 基準の3通り、サムネイルが 64px / 128px / 256px の3通り。`AI_GENERATION_GUIDE.md` は存在しない `items.json` 方式を説明している。README の「設定 → URLから取得」は画面に存在しない。
- **取り込みが「全部入れ替え」**。名前で照合し、取り込んだものに無い既存データは削除される（`assetStorage.ts:1693-1808`）。その結果:
  - 中身が正しくないフォルダや ZIP を選ぶと、既存データが全部消えてから「見つかりません」と出る。
  - ドール1体だけ、新しい服だけを取り込むと、他が全部消える。
  - 1枚でも画像が壊れているとプリセット全体が失敗し、その分は「無いもの」として削除される。
  - 取り込むたびに ID が変わるので、着ていた服・選んでいたドールや背景が外れる。古い画像レコードは消えず、容量が増え続ける。
- **フォルダ取り込みと ZIP 取り込みがコピー実装**（各約 570 行）で、挙動が食い違っている（ZIP は手作りサムネイルを縮小しない、ファイル名方式で ID 付きのときサムネイルを見つけられない、など）。
- `scripts/optimize-images.py` は元画像を上書きし、アプリが読まない `public/assets` を対象にしている。

## 3. 目標・やらないこと

### 目標（完了時に同じ手順で測る）

| 項目 | 現状 | 目標 |
|---|---|---|
| JS 合計（gzip） | 272 KB | 130 KB 以下 |
| PWA 事前キャッシュ | 3.8 MB | 0.6 MB 以下 |
| サンプルプリセットの保存容量 | 83 MB | 30 MB 以下 |
| 起動直後の JS ヒープ | 92 MB | 30 MB 以下 |
| ドラッグ中の服の再描画・保存書き込み | 39 回・40.5 MB | 0 回・0 バイト |
| 着ている服の保存データ | 1枚あたり約 250 KB | 1枚あたり 300 バイト以下 |
| 変更のないプリセットの再取り込み | 約 9 秒 | 約 2 秒以下（未変更ファイルは処理しない） |
| 1点の素材に必要な作業 | PNG ＋ 手作りサムネイル ＋ 透過処理 ＋ 命名ルール | PNG をカテゴリフォルダに置くだけ |

### やらないこと

- 新しい遊びの追加（アニメーション、着せ替え以外のモード、AI 生成の組み込みなど）。
- React をやめること（画面部品はすべて React で、効果に対して作り直しの量が大きい）。
- git 履歴の書き換え（`.git` は 478 MB あるが、履歴改変は別途判断する）。

### こうなったら失敗

- 既存のプリセット ZIP が取り込めなくなる、または同じ ZIP で服の位置や重なり順が変わる。
- 今できる操作（下の「残す機能」）ができなくなる。
- 見た目の画質が今より落ちる。

### 残す機能（今の遊びの定義）

ドール切り替え（切り替え時に服をリセット）／カテゴリ一覧と並び順／フォルダ番号による重ね順／同カテゴリは着替え、`_overlap` は重ね着／ドラッグで着せる／カテゴリの「なし」／背景の選択と「なし」／調整（移動・拡大縮小・回転・最前面・色相）／ドールの移動・拡大縮小／リセット（背景も外す）／写真の保存・共有（横画面は正方形、縦画面は全体）／状態の自動保存と復元／縦画面・横画面／オフライン動作（PWA）／フォルダ取り込み・ZIP 取り込み。

## 4. 進め方の候補と選択

描画まわりをどうするかで全体の形が変わる。3案を比べた。

| 案 | 内容 | 良い点 | 悪い点 |
|---|---|---|---|
| A. PixiJS を残して使い方を直す | 再描画の条件を直し、スプライトを使い回す | 変更が最小 | JS の 57% が残る。WebGL コンテキストロストが残る。調整プレビュー（CSS）との二重実装が残る |
| **B. Canvas 2D に置き換える（採用）** | 「場面を描く関数」を1つ作り、画面表示・調整中のプレビュー・写真の3つで同じ関数を使う | PixiJS が不要になる。描画が1系統になり、ずれが原理的に起きない。WebGL を使わないのでコンテキストロストが無い。写真が画面サイズに依存しなくなる | 色相変更を自前で実装する必要がある（行列は既に `ItemAdjustPanel.tsx:19` にある）。描画を書き直す |
| C. DOM の `<img>` を重ねる | 各レイヤーを CSS transform で配置 | ライブラリ不要。実装が最も少ない | 写真を撮るために結局 Canvas の描画も必要で、二重実装が残る |

**B を採用する（私の判断）。** 理由は、このゲームの描画量（静止画十数枚、変化があったときだけ）なら Canvas 2D で十分で、軽さと「調整プレビューのずれ」という2つの問題の根を同時に断てるから。

保存と取り込みは、案を比べるまでもなく「画像はバイナリで保存・必要な分だけ読む・ID を安定させる・取り込みは1実装」に作り直す。

## 5. 設計

### 5.1 データの持ち方

- **画像はバイナリで IndexedDB に保存する**（`ArrayBuffer` と MIME タイプ。`Blob` を直接保存しないのは、iOS Safari の過去の不具合を避けるため）。base64 文字列はやめる。
- **起動時に読むのは、現在のドールの「メタデータ＋サムネイル」だけ**。フルサイズ画像は、着せたとき・ドールや背景を表示するときに読む。
- **ID はパスから作る**（例: `doll-アニメ/clothing/04_5_トップス/セーター`）。同じファイルを取り込み直しても ID が変わらない。
- **ファイル内容のハッシュを保存する**。再取り込み時、ID とハッシュが同じファイルは処理を飛ばす。
- **服とドールは「透明でない部分の外接矩形」で切り抜いて保存する**。元キャンバス内での位置（左上座標と元キャンバスの大きさ）をメタデータに持つ。描画時はその位置に戻すので、見た目は今と同じ。靴や帽子のようにキャンバスの大半が透明な素材で、メモリと描画コストが大きく減る。
- **基準座標は今と同じ**: 取り込み時に長辺 1024px に正規化し、ドールと服は中心を合わせ、表示倍率は「表示高さ ÷ 1024」。既存プリセットの位置関係は変わらない。
- **保存形式**: 背景は JPEG（品質 0.85 前後）。服とドールは、ブラウザが WebP で書き出せれば WebP、できなければ PNG（書き出し結果の MIME タイプで判定）。WebP の品質は実機で元画像と見比べて決め、差が見えるなら PNG のままにする（画質を落とさないことを優先）。
- **localStorage に置くのは小さな状態だけ**: 選択中のドール ID・背景 ID、ドールの位置と倍率、着ている服（ID・着た順・調整値のみ）、バージョン番号。
- **調整値はドール基準の単位で保存する**。位置のずらし量は「基準 1024 に対する値」で持ち、描画時に表示倍率とドールの倍率を掛ける。画面の向き・端末・ドールの拡大縮小が変わっても、服はドールに付いたまま。
- **旧データの扱い（私の判断・要確認）**: 自動変換はしない。更新後の初回起動で旧データを検出したら「保存方式が新しくなりました。プリセットをもう一度取り込んでください」と案内し、新形式での取り込みが成功した時点で旧データを消す。ID の付け方が変わるため、変換するより取り込み直すほうが確実。

ストアの分け方、キー設計、キャッシュの持ち方は実装者に任せる。

### 5.2 取り込み

- **実装は1つ**。フォルダと ZIP は「パスとバイト列の一覧」に変換するだけの薄い入口にし、以降の処理を共通にする。
- **1枚あたりの処理（デコードは1回）**:
  1. ハッシュを計算し、既存と同じなら飛ばす。
  2. デコードして長辺 1024px に正規化する。
  3. 服・ドールで、画像に透明部分がまったく無い場合のみ、背景を自動で透明にする。四隅の色を背景色とみなし、画像の縁からつながっている同系色だけを消す（服の内側の緑は残る）。縁はなめらかにする。
  4. 右下の透かし除去は条件付きにする。右下隅の近くに、本体とつながっていない小さな塊があるときだけ消す。
  5. 外接矩形で切り抜き、保存形式に書き出す。
  6. 切り抜いた画像からサムネイルを作る（長辺 192px 前後）。同名の `_サムネ` `_thumb` `_thumbnail` があればそちらを使う。
- **同期のルール**:
  - 取り込みに含まれる `doll-*` フォルダごとに、追加・更新・削除（そのフォルダから無くなったもの）を行う。
  - 取り込みに含まれないドールには触らない。
  - 有効なドールが1体も無ければ、何も変更せずに中止する。
  - 削除は、そのドールの全ファイルを処理し終えてから行う。
  - 画像1枚の失敗は、その1枚を飛ばして続行する。
  - ルート直下の `backgrounds/`（全ドール共通の背景）は今までどおり受け付ける。
- **命名ルールは今のものをすべて受け付ける**（フォルダ方式・ファイル名方式・番号なしの英語フォルダ名）。直すのは次の点だけ:
  - 並び順の小数（`04_1.5_ドレス`）を解釈する。
  - ファイル名方式の癖（`overlap_` 直後のアンダースコア、ZIP で `categoryOrder` が入らない、ID 付きでサムネイルが見つからない）を直す。
- **進み具合と結果を見せる**: 取り込み中は「32 / 101」の進捗、終了後は「追加・更新・削除・変更なし」の件数と、注意事項の一覧（背景を自動で透明にした、読めなかった、どのカテゴリにも入らなかった、など）。
- JSZip は今までどおり、取り込み時だけ読み込む。

### 5.3 描画

- **場面を描く関数を1つにする**。入力は「背景・ドール・着ている服（重ね順に並べ済み）・ドールの位置と倍率・表示領域」、出力は Canvas への描画。状態を持たない。
- **同じ関数を3か所で使う**: 画面表示、調整中のプレビュー（調整中の値をそのまま渡して描く。CSS のプレビューは廃止）、写真（画面外の Canvas に描く。切り取り範囲は今と同じ）。
- **描くのは変化があったときだけ**。常時ループは持たない。調整中のドラッグは 1 フレームに 1 回までにまとめる。
- **レイアウトの計算は今と同じ**: 背景は画面の高さを一辺とする正方形で、メニューと右ボタンを除いた領域の中央。ドールの位置は背景に対する %。ドールの高さは横画面で画面の 90%、縦画面で 75%。
- **高精細表示**: `devicePixelRatio` に合わせる（上限 2）。縮小時は高品質補間を使う。
- **色相**: PixiJS の `ColorMatrixFilter.hue()` と同じ行列を画素に適用し、「アイテム＋色相」ごとに結果を保持する。保存済みの色相値がそのまま同じ色になる。スライダー操作中の追従方法（間引き、縮小版で計算など）は実装者に任せる。
- **デコード済み画像の管理**: 表示に必要なもの（背景・ドール・着ている服）と、直前に脱いだ数枚だけを保持し、それ以外は解放する。
- 調整中の描画が実機で重い場合に限り、「調整中のアイテムより下」「より上」をそれぞれ1枚にまとめて保持する。実機で測ってから判断する。
- 削除するもの: PixiJS、`PixiEngine`、プレースホルダー人形の描画、カスタム顔、`?test=true` の回避処理（Canvas 2D はテスト環境でも動く）。

### 5.4 操作

残す機能はそのままに、次を変える。

- **タップでも着られるようにする**（横画面・縦画面とも）。ドラッグで着せる操作も残す。着ている服をもう一度タップすると脱げる。
- **一覧はサムネイルの上でもスクロールできるようにする**。動かした方向で判定する: 一覧の流れる方向（横画面は縦、縦画面は横）ならスクロール、ドール側への動きならドラッグ。右側 30px の余白は不要になるので、サムネイルを大きくする。
- **着せても脱がせてもカテゴリに留まる**。戻るのは「もどる」を押したときだけ。
- **調整する対象を選べるようにする**。調整モードで、ドールの上の服をタップするとその服が対象になる（重なっているときは上の服が優先。透明部分は当たらない）。何もないところ・ドール本体をタップするとドールが対象になる。調整ボタンを押した直後の対象は、今と同じく最後に着せた服（何も着ていなければドール）。これで、服を脱がせなくてもドールを動かせる。
- **ドラッグ中の表示を軽くする**。指に付いてくるサムネイルは、`App` 全体を再レンダリングせずに動かす。
- **画面の向きを変えても表示が保たれる**（5.1 の調整値と 5.3 の描画で解決）。
- **初回起動の案内**。プリセットが無いときは、空の画面ではなく「プリセットを取り込む」ボタンを中央に出す。

文字の大きさやボタンの寸法など細部は実装者に任せる（タッチ対象は 44px 以上）。

### 5.5 素材づくり

- **作者が守るルールを1つにする**: 「ドールと同じ大きさのキャンバスに、ドールに重ねた位置で描いた PNG を、`doll-名前/clothing/重ね順_並び順_カテゴリ名/` に置く」。サムネイル・透過・切り抜き・縮小・ファイル名の ID は不要（5.2 が自動で行う）。
- **説明書を1つにまとめる**。`README.md` の該当部分、`docs/AI_GENERATION_GUIDE.md`、テンプレート内の 3 つの txt を、実際の動作に合わせた1つの「素材の作り方」に統合する。AI 画像生成のプロンプト例はその中の1章にする。README の事実と違う記述（グリーンバックの GPU 処理、URL から取得、など）を直す。
- **テンプレート**: 正しいフォルダ構成の見本を `preset-template/` に置く（今の英語フォルダ名の古い見本を置き換える）。
- **`scripts/optimize-images.py` は廃止**。取り込みが同じことを自動で行うため。
- **リポジトリの整理**: `*.png~` を削除する。`preset-original/`（94 MB）は追跡をやめて Releases の ZIP に一本化するか、残すかを決める（要確認）。

## 6. 進める順番

各段階は単独でリリースできる大きさにし、段階ごとに 2 章と同じ計測をして数値を記録する。

| 段階 | 内容 | 主な効果 |
|---|---|---|
| 0. 安全網と即効修正 | E2E テストを現状の画面に合わせて作り直す（小さなテスト用プリセットで「取り込み → 着せる → 調整 → 再読み込みで復元 → 向きを変える → 写真」）。着ている服の配列を安定させてドラッグ中の再描画を止める。着ている服の保存を ID と調整値だけにする。未使用コード・未使用画像を削除し、アイコンを圧縮する。README の誤記を直す。ESLint エラーとテストの未処理エラーを解消する | ドラッグが軽くなる。保存失敗の危険が無くなる。事前キャッシュが 3.8 MB → 1 MB 未満 |
| 1. 保存と取り込み | 5.1 と 5.2。この段階では PixiJS のまま、切り抜き画像を元の位置に描く | 保存容量・起動メモリ・取り込みの安全性。サムネイルと透過の自動化 |
| 2. 描画 | 5.3。PixiJS を外す | JS が半分以下。調整のずれ・向き変更・コンテキストロストの解消 |
| 3. 操作 | 5.4 | タップ着用、スクロール、調整対象の選択 |
| 4. 素材の説明書 | 5.5 | 作者の手順が1つになる |

- 段階 0 は他に依存せず、効果が大きく危険が小さいので最初に行う。
- 段階 3 のうち「タップで着る」「カテゴリに留まる」「一覧のスクロール」は描画に依存しないので、操作性を先に良くしたい場合は段階 0 の直後に前倒しできる。
- 横→縦でドールが消える問題は、段階 0 で原因を調べる。PixiJS 固有で直しにくい場合は段階 2 で解消する。

## 7. テスト方針

- **ユニットテスト**（画面を使わない部分）: フォルダ名・ファイル名の解釈、外接矩形の計算、背景の自動透過、同期の差分計算、レイアウト計算、当たり判定、色相行列。
- **E2E テスト**: テスト内で生成した小さなプリセットで、段階 0 のシナリオを通す。描画結果は画素を数点サンプリングして確認する（服を着たら色が変わる、向きを変えても空にならない）。
- **互換性の確認**: `preset-original` のサンプルを取り込み、段階 1・2 の前後で同じ服の組み合わせの写真を撮って比べる（位置と重なり順が変わらないこと）。
- **実機確認**: iPad Safari で、取り込み・ドラッグ・調整・向き変更・バックグラウンドからの復帰を各段階で確認する（開発環境では確認できないため、作者に依頼する）。

## 8. 確認したい点

1. **旧データは「更新後に1回だけ取り込み直し」でよいか**（5.1）。作者以外に、取り込み済みのデータを持つ利用者がいるかどうかで判断が変わる。
2. **`preset-original/`（94 MB）をリポジトリから外してよいか**（5.5）。
3. **`_movable` の扱い**。README は「ドロップした位置に置かれる」と書いているが、現在のコードはドロップ位置を使っておらず、他の服と同じ位置に着る（その後の調整で動かす）。本設計は現在の動作を維持する。README どおり「落とした場所に置く」にしたい場合は段階 3 に追加する。
4. **素材づくりの今の手順**（AI で生成 → 緑背景 → 透過 → サムネイル作成、を PC と iPad のどちらで行っているか）。アプリ内で1枚ずつ追加・削除する画面が必要かどうかが、これで決まる。本設計には含めていない。
