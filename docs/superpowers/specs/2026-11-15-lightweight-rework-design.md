# きせかえゲーム 軽量化・操作性・素材準備の改善 設計書

- 作成日: 2026-11-15
- 対象: v0.9.6（コミット `cbb39f0`）
- 状態: **承認済み（2026-11-16）**

## 1. ねらい

今の遊び（ドールを選ぶ → カテゴリから服を選んで着せる → 位置・大きさ・傾き・色を調整 → 背景を変える → 写真を撮る）は変えずに、次の3つを達成する。

1. **軽量さ**: 読み込むプログラム、保存容量、メモリ、操作中の処理を減らす。
2. **操作性の良さ**: 子どもが iPad で迷わず・待たずに遊べる。
3. **画像素材の準備の容易さ**: AI が作った画像を選んでカテゴリを決めるだけで、切り抜き・位置合わせ・サムネイル作成・iPad への配信まで済むようにする。

## 2. 現状レビュー（実測）

計測条件: 本番ビルドを Chromium（1180×820、ソフトウェア描画）で起動し、`preset-original/preset-template/doll-アニメ`（ドール1・服81・背景20、ZIP 61MB）を取り込んで操作した。ソフトウェア描画なので時間の絶対値は実機より遅いが、回数とバイト数は環境に依存しない。

| 項目 | 現状 |
|---|---|
| JS 合計（minify 後） | 約 922 KB（gzip 約 272 KB）。内訳: PixiJS 525 KB / React 193 KB / JSZip ほか 111 KB / アプリ本体 94 KB |
| PWA の事前キャッシュ | 3.8 MB。うち未使用のドール画像 2 枚で 2.1 MB、アイコン 1 枚で 755 KB |
| 取り込み後の保存容量（IndexedDB） | 83 MB。全画像を base64 文字列で保存（204 レコード） |
| 起動直後の JS ヒープ | 92 MB。全ドール・全服・全背景の画像を文字列のまま全部メモリに載せる |
| 服を1枚着た状態で、別の服を 40 回ぶんドラッグ | 服全体の再描画が 39 回、localStorage への書き込みが 40 回・計 40.5 MB |
| 着ている服の保存データ | 8 枚で 2.07 MB（画像そのものを含む）。localStorage の上限は約 5 MB |
| ZIP の取り込み時間 | 約 9 秒（再取り込みでも毎回すべて処理し直す） |

### 2.1 軽さの問題

- **ドラッグ中の無駄な再描画（最大の問題）**。`useDressUp.getEquippedItems()` が呼ばれるたびに新しい配列を返すため（`src/hooks/useDressUp.ts:129`）、`App` が再レンダリングされるたびに「着ている服が変わった」と判定される。ドラッグ中は指が動くたびに `App` が再レンダリングされるので（`src/App.tsx:429` の `setDraggingPreview`）、毎回、服の全スプライト作り直し＋テクスチャ焼き込み（`src/engine/PixiEngine.ts:411-563`）と、着ている服の保存（`src/App.tsx:286`）が走る。
- **保存データに画像本体が入っている**。着ている服の保存（`src/services/stateStorage.ts:40`）がアイテムを丸ごと JSON 化しており、画像の data URL が含まれる。大きい服が数枚重なると上限を超え、保存が黙って失敗する（`catch` でログのみ）。
- **画像を base64 文字列で持っている**。保存容量が約 1.33 倍になり、メモリ上ではさらに膨らむ。起動時に全ドール分を逐次読み込む（`src/App.tsx:206-228`、`src/services/assetStorage.ts:469-528`）。
- **PixiJS が JS の 57% を占める**。このゲームが描くのは「静止画を十数枚、位置・拡大・回転・色相を付けて重ねる」だけで、毎フレームの描画もアニメーションもない。現在は Ticker を1秒後に止める、`cacheAsTexture` で焼き込む、といった「Pixi を止めるための工夫」が入っている。
- **使われていないコードが約 1/3**。`App` から到達できないもの: `AIFaceGenerator` `CategorySelector` `ClothingItem` `ClothingPalette` `DollControlPanel` `DraggableClothingItem` `ItemImporter` `ItemManager` `ChromaKeyFilter` `EdgeTrimFilter` `aiGenerator` `dataManager`、および `assetStorage.ts` 内の約 510 行。`DrawingCanvas` `EraserCanvas` は描画されているが、有効にする手段がない。合計およそ 3,900 行（全体は約 12,000 行）。
- **リポジトリ**。`.gitignore` に入っている `preset-original/`（94 MB）と `*.png~` バックアップ 14 個が追跡されている。

### 2.2 操作性の問題

- **横画面ではタップしても着られない**（実測: タップ後の装備数 0）。10px 以上ドラッグしてメニューの外で離す必要がある（`src/components/DressUpMenu.tsx:546-558`）。縦画面は逆にタップのみ。
- **アイテム一覧は、サムネイルの上ではスクロールできない**。サムネイル全体が `touch-action: none` のため、右側 30px の余白でしかスクロールできない（`DressUpMenu.tsx:570, 717`）。
- **着せるたび・脱がせるたびにカテゴリ一覧へ戻される**（縦画面の着用時、両画面の「なし」）。同じカテゴリで何着も試しにくい。
- **調整できるのは「最後に着せた1枚」だけ**（`src/App.tsx:344`）。前に着せた服を直すには着せ直す必要がある。**ドールの移動・拡大は、服を全部脱がせないとできない**（`src/App.tsx:337`）。
- **調整した位置が画面サイズに依存する**。調整量を画面ピクセルで保存しているため（`PixiEngine.ts:471`）、画面の向きや端末が変わると服がずれる（実測: 横画面で動かしたドレスが縦画面で大きくずれた）。ドールを拡大縮小しても調整量は追従しない。
- **調整プレビューが別実装**。調整中は Pixi ではなく CSS の `<img>` でプレビューしている（`src/components/ItemAdjustPanel.tsx:544-615`）。2つの描画の位置合わせが難しく、直近 30 コミットのうち 12 件がこのずれの修正。
- **画面を横→縦に変えるとドールが消える**（実測。再読み込みで復帰。実機での確認が必要）。
- README に「WebGL コンテキストロストが稀に発生」と既知の問題として記載あり。

### 2.3 素材準備の問題

- **サムネイルが実質手作り**。自動サムネイルはキャンバス全体を 128px に縮めるだけなので（`assetStorage.ts:125-160`）、靴や帽子は豆粒になる。サンプルでは 91 点中 84 点に手作りの `_サムネ` 画像がある。
- **緑背景は自動で抜けない**。README は「グリーンバック自動透過」と書いているが、描画時のフィルタは削除済み（`PixiEngine.ts:815-830` は空のメソッド）、取り込み時にも実行されない。唯一残っているのは調整プレビュー用の処理で（`ItemAdjustPanel.tsx:218-226`、`assetStorage.ts:229-275`）、調整中だけ透過して見え、透過済みのコピーが `{id}_transparent` として IndexedDB に追加保存される。サンプルの 4 点（ショートパンツ、ロングスカート、赤いチェックのスカート、ショートヘア）は不透明な緑背景のまま。
- **右下 160px を無条件に消す**（透かし除去、`assetStorage.ts:193-221`）。右下まで描かれた素材は欠ける。幅 495px の画像では幅の 1/3 が対象になる。
- **命名ルールが2系統あり、書類と食い違う**。フォルダ方式（`04_5_トップス/名前.png`）とファイル名方式（`4_5_トップス_名前_ID.png`）があり、後者はどの書類にも書かれていない。ファイル名方式では、末尾の英数字が ID 扱いになって名前が欠ける、`movable` を指定できない、などの癖がある。README の例 `04_1.5_ドレス` は小数を解釈できず、意図どおりに動かない。
- **説明書が 5 つあり互いに矛盾する**（`README.md`、`docs/AI_GENERATION_GUIDE.md`、`preset-template/README.txt`、`AI_PROMPT_GUIDE.txt`、`着せ替えアイテムプロンプト例.txt`）。推奨サイズが 512×1024 / 800〜1200px / 1024 基準の3通り、サムネイルが 64px / 128px / 256px の3通り。`AI_GENERATION_GUIDE.md` は存在しない `items.json` 方式を説明している。README の「設定 → URLから取得」は画面に存在しない。
- **取り込みが「全部入れ替え」**。名前で照合し、取り込んだものに無い既存データは削除される（`assetStorage.ts:1693-1808`）。その結果:
  - 中身が正しくないフォルダや ZIP を選ぶと、既存データが全部消えてから「見つかりません」と出る。
  - ドール1体だけ、新しい服だけを取り込むと、他が全部消える。
  - 1枚でも画像が壊れているとプリセット全体が失敗し、その分は「無いもの」として削除される。
  - 取り込むたびに ID が変わるので、着ていた服・選んでいたドールや背景が外れる。古い画像レコードは消えず、容量が増え続ける。
- **フォルダ取り込みと ZIP 取り込みがコピー実装**（各約 570 行）で、挙動が食い違っている（ZIP は手作りサムネイルを縮小しない、ファイル名方式で ID 付きのときサムネイルを見つけられない、など）。
- `scripts/optimize-images.py` は元画像を上書きし、アプリが読まない `public/assets` を対象にしている。

## 3. 作者から決まったこと（2026-11-16）

- **プリセット方式をやめる**。服の画像はアプリと一緒に GitHub Pages から配信し、iPad では開くだけで最新の服が出る。ZIP・フォルダの取り込みは廃止する。
- **iPad の横画面固定**でよい。縦画面レイアウトは廃止する。
- **今の素材づくり**: PC で、基準ドールに服を着せた画像を AI に作らせ、ドール部分を Photoshop 等で切り抜いている。困っているのは (1) AI の出力でドールの位置が少しずれること、(2) 毎回手で切り抜くこと。AI に切り抜かせるのはうまくいかない。
- 作者から届いた AI 出力のサンプルは、ドールが単色のシルエット（緑または黒）、背景が単色（白またはマゼンタ）の 2000×2000 画像だった。

## 4. 試作でわかったこと（切り抜きと位置合わせ）

サンプル 3 枚に対し、捨てる前提のスクリプトで自動処理を試した（コードは残していない）。

- **切り抜き**: 「画像の縁からつながっている背景色」と「シルエット色」を消す方法で、緑シルエットの 2 枚（上下セット、ドレス）は手直しがほぼ不要な結果になった。服の内側の白いハイライトは残せた。右下の Gemini のマークも除去できた。
- **位置合わせ**: 「シルエットはドールの内側にあり、背景はドールに重ならない」という条件で、最も合う位置と倍率を探す方法が機能した。サンプルに人工的なずれ（4% の拡大縮小と数十 px の移動）を加えて試し、倍率は誤差 1% 未満、位置は誤差 4px 以内（1024px 基準）で復元できた。届いたサンプル 3 枚そのものは、ほぼずれていなかった。
- **うまくいかなかった例**: 黒いシルエットに紺色のスカートの 1 枚は、スカートのひだの影がシルエットと同じ色とみなされて欠けた。色が近いと区別できない。
- **残った粗**: 服のふちにシルエット色がわずかに残る箇所、首飾りの内側など背景が閉じ込められた箇所。本実装で詰める対象とし、最後は手直しブラシで直せるようにする。

結論: シルエットの色を服と離れた色（基本は明るい緑、緑の服のときはマゼンタ）にすれば、自動化できる見込みが高い。黒いシルエットは暗い服で失敗するので使わない。

## 5. 目標・やらないこと

### 目標（完了時に 2 章と同じ手順で測る）

| 項目 | 現状 | 目標 |
|---|---|---|
| JS 合計（gzip） | 272 KB | 100 KB 以下（PixiJS と JSZip が不要になる） |
| PWA 事前キャッシュ | 3.8 MB | 0.5 MB 以下 |
| 端末内の保存（IndexedDB） | 83 MB | 使わない（ブラウザのキャッシュのみ） |
| 配信する画像の合計（サンプル相当） | ZIP 61 MB | 25 MB 以下 |
| 起動直後の JS ヒープ | 92 MB | 30 MB 以下 |
| ドラッグ中の服の再描画・保存書き込み | 39 回・40.5 MB | 0 回・0 バイト |
| 着ている服の保存データ | 1枚あたり約 250 KB | 1枚あたり 300 バイト以下 |
| 素材 1 点に必要な作業 | AI 生成 → 手で切り抜き → サムネイル作成 → 命名 → ZIP 化 → iPad で取り込み | AI 生成 → スタジオに入れてカテゴリを選ぶ → 公開 |

### やらないこと

- 新しい遊びの追加。
- React をやめること。
- git 履歴の書き換え。
- iPad 上での素材追加（素材づくりは PC で行う）。
- 人の確認を通さない自動公開。
- 縦画面・スマートフォン向けのレイアウト。

### こうなったら失敗

- 今ある服（サンプルの 91 点）が新方式に移したあと、位置や重なり順が変わる。
- 下の「残す機能」ができなくなる。
- 見た目の画質が今より落ちる。

### 残す機能（今の遊びの定義）

ドール切り替え（切り替え時に服をリセット）／カテゴリ一覧と並び順／カテゴリごとの重ね順／同カテゴリは着替え、重ね着可のカテゴリは重ね着／ドラッグで着せる／カテゴリの「なし」／背景の選択と「なし」／調整（移動・拡大縮小・回転・最前面・色相）／ドールの移動・拡大縮小／リセット（背景も外す）／写真の保存・共有（背景の正方形）／状態の自動保存と復元／オフライン動作（PWA）。

なくなるもの: フォルダ取り込み・ZIP 取り込み・設定画面・縦画面レイアウト。

## 6. 進め方の選択

- **描画**: PixiJS を残す案、Canvas 2D に置き換える案、DOM の `<img>` を重ねる案を比べ、**Canvas 2D に置き換える**（私の判断）。描くのは静止画十数枚で変化時だけなので十分。JS の 57% が不要になり、表示・調整・写真を同じ処理で描けるので、調整プレビューのずれが原理的に起きない。DOM 案は写真のために結局 Canvas の描画が要り、二重実装が残る。PixiJS を残す案は容量とコンテキストロストが残る。
- **素材の届け方**: プリセット（ZIP を iPad で取り込む）を続ける案と、アプリと一緒に配信する案を比べ、**配信する**（作者の決定）。取り込み処理・IndexedDB・JSZip・設定画面が不要になり、最も軽くなる。
- **切り抜きの自動化**: 基準ドール画像との差分を取る案と、単色シルエットを色で抜く案がある。届いたサンプルがシルエット方式だったので、**色で抜く＋シルエットの形でドールに位置合わせする**（4 章の試作で確認）。

## 7. 設計

### 7.1 配信する素材の形

- 置き場所は `public/content/`。ビルドでそのまま GitHub Pages に載る。
- **一覧ファイル**（`manifest.json`）が全体を表す: ドール（名前、画像、キャンバスの大きさ）、ドールごとのカテゴリ（表示名、重ね順、メニューの並び順、重ね着可、自由配置）、アイテム（名前、カテゴリ、画像、サムネイル、元キャンバス内での位置と大きさ）、背景（ドール専用か共通か）。
- **順番や種類はファイル名ではなく一覧ファイルに書く**。番号付きフォルダ名・ファイル名の規則はなくなる。
- **アイテム画像は透明でない部分で切り抜いて保存**し、元の位置を一覧ファイルに持つ。描画時に戻すので見た目は同じ。基準は今と同じ（ドールのキャンバスは長辺 1024px、服は中心を合わせて同じ縮尺）。
- **形式**: 服とドールは WebP、背景は JPEG、サムネイルは長辺 192px 前後の WebP。WebP の品質は元画像と見比べて決め、差が見えるなら劣化なしの設定にする（画質優先）。
- **ファイル名に内容のハッシュを入れる**。画像を差し替えると名前が変わるので、古いキャッシュが残っても混ざらない。
- **アプリ側の読み込み**: 起動時に一覧ファイルを取得する（オンラインなら最新、オフラインなら前回のもの）。サムネイルは表示するときに、フルサイズ画像は着せたときに取得する。取得した画像はサービスワーカーがキャッシュする。加えて、起動後の空き時間に現在のドールの全画像を先読みし、オフラインでも全部の服で遊べるようにする。
- **端末に保存するのは小さな状態だけ**（localStorage）: 選択中のドール・背景、ドールの位置と倍率、着ている服（ID・着た順・調整値）。調整値はドール基準の単位で持つ（画面の大きさやドールの拡大縮小が変わっても服がドールに付いたまま）。
- **旧データ**: 新バージョンの初回起動時に、古い IndexedDB と古い localStorage の項目を削除する。着ていた服の復元は引き継がない。

### 7.2 素材スタジオ（PC 用の制作ツール）

リポジトリ内に置く開発専用の画面。PC で `npm run studio` を実行するとブラウザで開く。ゲーム本体には含めない。

**服を追加する流れ**

1. ドールを選び、AI が作った画像を入れる（複数枚まとめて可）。
2. 自動で次を行う: 背景色とシルエット色の検出 → 背景とシルエットの除去 → 右下のマークなど離れた小片の除去 → シルエットの形を使ったドールへの位置・倍率合わせ → 切り抜き → サムネイル作成。
3. ドールに着せた状態のプレビューを見る。必要なら手直しする: 消しゴム／復元ブラシ、矢印キーでの位置の微調整、倍率の微調整。
4. カテゴリ（既存から選ぶか新規作成）と名前を決めて保存する。`public/content/` に画像が書き出され、一覧ファイルが更新される。

**そのほかの機能**

- 一覧の管理: アイテムの名前変更・カテゴリ移動・削除、カテゴリの並び替え（重ね順とメニュー順）、重ね着可・自由配置の切り替え。
- 背景の追加（画像を選ぶだけ。自動で縮小・JPEG 化・サムネイル作成）。
- ドールの追加（透過 PNG を選ぶ）。
- **AI に渡す基準画像の書き出し**: ドールの形を単色で塗ったシルエット画像（白背景）を、緑・マゼンタで書き出す。毎回同じ基準を使えるようにする。
- **公開ボタン**: `public/content/` の変更をコミットして push する。あとは今までどおり GitHub Actions が配信する。
- すでに切り抜き済みの透過 PNG も、そのまま追加できる（自動処理は切り抜きとサムネイル作成だけになる）。

**自動処理の決まり（試作から）**

- 背景は「背景色で、画像の縁からつながっている部分」だけを消す（服の内側の白は残す）。背景色に囲まれて閉じた部分は、シルエットに接していれば消す。
- シルエットは単色とみなし、その色に近い画素を消す。ふちに残るシルエット色は除去する。
- 位置合わせは、まず粗く探し、次に細かく探して 1px 程度まで詰める。合い具合が悪いとき（シルエットがドールと違う、など）は警告を出す。
- 背景色・シルエット色と服の色が近くて区別できないときは、警告を出して手直しに回す。

画像処理の具体的な方法、ファイルの書き出し方、画面の構成は実装者に任せる。画像処理部分は画面なしでテストできる形にする。

### 7.3 今ある素材の移行

- 1 回きりのスクリプトで、`preset-original/preset-template/` の内容（ドール 2 体分の服と背景）を 7.1 の形に変換する。カテゴリ・重ね順・並び順・重ね着可はフォルダ名とファイル名から読み取る。手作りサムネイルは使わず、自動で作り直す。
- 緑背景のまま残っている 4 点は、7.2 と同じ処理で透過する。
- 移行の前後で同じ組み合わせの写真を撮り、位置と重なり順が変わらないことを確かめる。
- 確認後に削除するもの: `preset-original/`、`preset-template/`、`scripts/optimize-images.py`、`public/assets/dolls/`、`*.png~`。

### 7.4 描画

- **場面を描く関数を 1 つにする**。入力は「背景・ドール・着ている服（重ね順に並べ済み）・ドールの位置と倍率・表示領域」。状態を持たない。
- **同じ関数を 3 か所で使う**: 画面表示、調整中のプレビュー（CSS のプレビューは廃止）、写真（画面外の Canvas に描く。範囲と画素数は今と同じ: 背景の正方形、表示サイズ × `devicePixelRatio`）。
- **描くのは変化があったときだけ**。調整中のドラッグは 1 フレームに 1 回までにまとめる。
- **調整中の服は、今と同じく一番手前に描く**。完了すると本来の重ね順に戻る（「最前面」を押した場合を除く）。
- **レイアウトの計算は今の横画面と同じ**: 背景は画面の高さを一辺とする正方形で、メニューと右ボタンを除いた領域の中央。ドールの位置は背景に対する %。ドールの高さは画面の 90%。
- **高精細表示**は `devicePixelRatio` に合わせる（上限 2）。縮小時は高品質補間。
- **色相**: PixiJS の `ColorMatrixFilter.hue()` と同じ行列（`ItemAdjustPanel.tsx:19` に既にある）を画素に適用し、「アイテム＋色相」ごとに結果を保持する。
- **デコード済み画像**は、表示に必要なものと直前に脱いだ数枚だけ保持する。
- 調整中の描画が実機で重い場合に限り、調整中のアイテム以外を 1 枚にまとめて保持する。
- 削除するもの: PixiJS、`PixiEngine`、プレースホルダー人形、カスタム顔、`?test=true` の回避処理。

### 7.5 操作

- **タップでも着られる**。ドラッグも残す。着ている服をもう一度タップすると脱げる。
- **一覧はサムネイルの上でもスクロールできる**。縦に動かせばスクロール、ドール側へ動かせばドラッグ。右側 30px の余白をなくし、サムネイルを大きくする。
- **着せても脱がせてもカテゴリに留まる**。戻るのは「もどる」を押したときだけ。
- **調整する対象を選べる**。調整モードで、ドールの上の服をタップするとその服が対象になる（重なっていれば上の服、透明部分は当たらない）。何もないところ・ドール本体をタップするとドールが対象になる。調整ボタンを押した直後の対象は今と同じ（最後に着せた服、なければドール）。服を脱がせなくてもドールを動かせる。
- **ドラッグ中の表示を軽くする**。指に付いてくるサムネイルは、`App` 全体を再レンダリングせずに動かす。
- **横画面固定**。PWA の設定を横向きにする。縦に持ったときは「よこにしてね」と表示する。
- 設定ボタンと設定画面は廃止（取り込みがなくなるため）。バージョン表示は残す。

文字の大きさやボタンの寸法は実装者に任せる（タッチ対象は 44px 以上）。

### 7.6 説明書

- 5 つある説明書を、「素材の作り方」1 つにまとめる: AI に渡す基準画像の作り方、プロンプト例、シルエットの色の選び方、スタジオの使い方、公開のしかた。
- README を実際の動作に合わせて書き直す。

### 7.7 テーマから自動生成（ドール選択 → テーマ入力 → 候補 → 採用）

作者の決定（2026-11-16）: 文章の処理は Claude API、画像生成は Gemini API を使う。ドールは事前に数体に絞り、同じドールのアイテムを増やしていく。

**ドールごとの「型紙」を一度だけ作る**

ドールを登録するとき、次をまとめて保存する。以後の生成・加工・検品はすべてこれを基準にする。

- 透過のドール画像と、そこから自動で作る単色シルエット画像（緑・マゼンタ）。
- 体の部位の位置（頭、胴、腰、脚、足、手）。ドールの輪郭から自動で推定し、スタジオの画面で人が直せる。
- カテゴリごとの「あるはずの範囲」（靴は足のまわり、帽子は頭の上、など）と重ね順。
- 絵柄の説明文と、絵柄の見本にする既存アイテム数点。

**型紙の使いみち**

- **位置合わせ**: 生成画像のシルエットを型紙に合わせる（4 章の方法）。
- **部分を拡大して生成**: 靴・顔・髪・アクセサリーのような小さい品目は、その部位だけを切り出して拡大したシルエットを AI に渡し、できた画像を既知の倍率で元の位置に戻す。全身画像の中で小さく描かせるより細部が出る。
- **検品**: 切り抜いた結果が、そのカテゴリの「あるはずの範囲」に収まっているか、大きさが妥当かを数値で判定する。
- **プロンプト**: 絵柄の説明と見本画像を毎回同じものにして、絵柄を揃える。

**流れ**

1. スタジオでドールを選び、テーマを入力する（例:「海のおひめさま」）。作る品目数の上限も指定する。
2. Claude API が、カテゴリごとの品目リストと 1 点ごとの生成指示を作る。既存アイテムの名前を渡して重複を避ける。
3. 品目ごとに Gemini API で画像を生成する（型紙のシルエットと絵柄見本を添付）。
4. 7.2 と同じ処理で加工する。
5. 自動検品: 位置合わせの合い具合、範囲、欠け、色の近さを数値で判定し、さらに Claude API にドールへ着せた画像を見せて「指示どおりか・破綻がないか」を判定させる。不合格は理由を添えて作り直す（回数に上限を設ける）。
6. 合格した候補を、ドールに着せた状態で一覧表示する。人が採用・不採用・作り直しを選ぶ。採用分だけが `public/content/` に登録される。
7. 公開する。

**決めごと**

- API キーは PC 上の環境変数または git 管理外のファイルに置く。リポジトリには入れない（公開リポジトリのため）。
- 1 回の実行で使う画像生成の枚数に上限を設け、実行前に枚数の見積もりを表示する。
- Claude API のモデルは `claude-opus-5-5` を既定とし、設定で変えられるようにする。
- 自動公開はしない。必ず 6 の確認を通す。
- ドール本体を新しく生成する機能は、「候補を出して人が 1 体選び、型紙を作る」までとする。

**未確認の点**: Gemini API がシルエットをどの程度守るか、絵柄がどの程度揃うかは、この環境にキーがないため試せていない。この段階の最初の作業を「1 体のドールで 10〜20 点を生成し、合格率を測る」とし、その結果で部分拡大の要否や作り直し回数の上限を決める。合格率が低すぎる場合は、生成指示の出し方を見直してから先へ進む。

## 8. 進める順番

各段階は単独でリリースできる大きさにし、段階ごとに 2 章と同じ計測をして数値を記録する。

| 段階 | 内容 | 主な効果 |
|---|---|---|
| 0. 安全網と即効修正 | E2E テストを現状に合わせて作り直す。着ている服の配列を安定させてドラッグ中の再描画を止める。着ている服の保存を ID と調整値だけにする。使われていないコードを削除する | ドラッグが軽くなる。保存失敗の危険がなくなる |

| 2. 素材スタジオ | 7.2 | 切り抜きと位置合わせの手作業がなくなる |
| 3. テーマから自動生成 | 7.7。最初に小規模な試行で合格率を測る | テーマを入れるだけで同じドールの服が増やせる |
| 4. 描画 | 7.4。PixiJS を外す | JS が 1/3 程度になる。調整のずれとコンテキストロストの解消 |

## 9. テスト方針

- **ユニットテスト**: 背景・シルエットの除去、位置合わせ（人工的にずらした画像を元に戻せること）、切り抜き、一覧ファイルの読み書き、レイアウト計算、当たり判定、色相行列。
- **E2E テスト**: テスト用の小さな素材で「着せる（タップとドラッグ）→ 調整 → 再読み込みで復元 → 写真」を通す。描画結果は画素を数点サンプリングして確認する。
- **スタジオ**: 作者のサンプル 3 枚を固定のテスト素材とし、緑シルエットの 2 枚が手直しなしで通ること、黒シルエットの 1 枚で警告が出ることを確かめる。
- **互換性**: 移行の前後で同じ組み合わせの写真を比べる（7.3）。
- **実機確認**: iPad Safari でのドラッグ・調整・オフライン動作・バックグラウンドからの復帰を各段階で確認する（開発環境では確認できないため、作者に依頼する）。

## 10. 決定事項（2026-11-16 作者承認）

1. **シルエットと背景の色は固定しない**。品目ごとに、いちばん切り抜きやすい色を自動で選ぶ。
   - 自動生成（7.7）では、Claude API が品目ごとに「服に使う予定の色」を出し、その色すべてから最も離れた 2 色をシルエット色と背景色に選ぶ（互いにも離れていること）。型紙のシルエット画像はその色で都度作る。
   - 生成後、実際の服の色とシルエット色・背景色の距離を測り、近すぎて欠けが疑われる場合は別の色の組で作り直す。
   - 手で入れた画像（7.2）は、画像から背景色とシルエット色を自動検出する。服と色が近い場合は警告を出す。
2. **公開ボタンは git の commit と push まで行う**。
3. **画像は別リポジトリに分ける**（例: `DressUpGame-content`。同じ `github.io` ドメインで配信し、アプリは一覧ファイルの URL を読む）。7.1 の `public/content/` は、この別リポジトリの内容と読み替える。開発時はローカルの内容を読めるようにする。
4. **`_movable`（自由配置）は現在の動作を維持する**（他の服と同じ位置に着て、調整で動かす）。
