# スタジオ（段階 2 と 3 を統合）: 計画と結果

- 作成日: 2026-11-16
- 設計書: `docs/superpowers/specs/2026-11-15-lightweight-rework-design.md`（4 章、7.2、7.7、10 章）
- 置き換えた計画: `2026-11-16-stage2-asset-studio.md`（PC 専用・手動生成の前提だった）
- 状態: **実装済み（v0.11.0、作業ブランチ）。AI を実際に呼ぶ部分は未確認**（下の「確かめられていないこと」）

## 1. 決めたこと

作者の決定（HANDOFF 2026-11-16 の 1〜9）に加え、作者から「決めることはすべておすすめで進めてよい」と指示があったので、次のとおり決めて進めた。

| 項目 | 決定 | 理由 |
|---|---|---|
| 進め方 | スタジオを「画面」と「API」に分け、API はまず PC 上で動かす。あとで同じ API をサーバーに載せる | キーを隠すにはサーバーが要る。PC が最も速く作れて確かめやすい |
| API の形 | HTTP サーバーに依存しない関数（リクエスト → レスポンス）にした（`tools/studio/api.ts`）。いまは Vite の開発サーバーに載せている | 載せ替えるとき、API 本体を書き直さずに済む |
| 画面 | アプリの別ページ（`studio.html`）。ゲームの読み込みには含めない。接続先は `VITE_STUDIO_API` で変えられる | 作者の決定 1 |
| サーバーの置き場所 | **まだ決めない**。画像処理に sharp（Node のネイティブ部品）を使うので、Node がそのまま動く所（Cloud Run、Fly.io、Render など）が素直。Cloudflare Workers は sharp が動かないので、選ぶなら画像処理を別の方法に替える必要がある | PC で動かして、使い方と量が分かってから選ぶほうが安全 |
| 有料化・利用者ごとの素材 | **この段階では扱わない**。スタジオが PC で動き、生成の合格率が分かってから、別の設計書にする | HANDOFF の提案どおり。大きな設計なので分ける |
| API キー | サーバー側の環境変数（`ANTHROPIC_API_KEY`、`GEMINI_API_KEY`）。画面には出さない | 作者の決定 5 |
| 金額の上限 | 画像生成の枚数で管理する。1 日 60 枚・1 回 30 枚（環境変数で変更可）。1 品目の生成は、作り直しを含めて 2 回まで。実行前に最大枚数を表示する | 費用のほとんどは画像生成。枚数なら実行前に確実に見積もれる。各サービスの管理画面の上限も併用してもらう |
| サンプル画像 3 枚 | 公開リポジトリに置いたままにする（テストの固定素材） | 作者提供の AI 生成画像で、テストがこれに依存する。問題があれば差し替える |
| 型紙の保存先 | 素材リポジトリの `studio/templates.json` | ドールと一緒に管理でき、別の PC でも同じ型紙になる |
| 部分拡大しての生成（設計書 7.7） | **作らない**。最初の試行の合格率を見てから決める | 設計書の決めごとどおり |

## 2. できたもの

| 場所 | 内容 |
|---|---|
| `src/pipeline/keyColors.ts` | 背景色とシルエット色の検出、切り抜きやすい色の自動選択（服の予定色からいちばん遠い 2 色。黒は使わない） |
| `src/pipeline/cutout.ts` | 背景とシルエットの除去。境目のまざった色、閉じ込められた背景、ふちの色残り（服の色に戻して半透明にする）、小さなかけらの除去 |
| `src/pipeline/align.ts` | シルエットの形でドールに位置・倍率を合わせる |
| `src/pipeline/bodyParts.ts` | ドールの輪郭から体の部位を推定、カテゴリごとの「あるはずの範囲」 |
| `tools/content/encode.ts`、`manifestEdit.ts` | 画像の書き出しと、素材フォルダの編集（追加・改名・移動・削除・並び替え・背景・ドール・不要な画像の掃除） |
| `tools/studio/processGenerated.ts` | AI 画像 1 枚 → ドールのキャンバスに合わせた服と警告 |
| `tools/studio/generate.ts`、`ai.ts`、`budget.ts` | テーマ → 企画（Claude）→ 画像生成（Gemini）→ 切り抜き → 数値の検品 → 見た目の検品（Claude）→ 作り直し。枚数の上限 |
| `tools/studio/api.ts`、`vitePlugin.ts` | API と、開発サーバーへの組み込み（`npm run studio`） |
| `studio.html`、`src/studio/` | 画面: ドールと型紙／服を追加／テーマから作る／背景／一覧／公開／ゲームで確認 |

守っていること: 書き込みは素材フォルダの `manifest.json`・`files/`・`studio/` だけ。一覧は検証してから一時ファイル経由で置き換える。既存のアイテムの ID は変えない。同じ名前は「別の服として追加」か「置き換える」を選ぶ。警告のある候補は、確認のチェックを入れるまで保存できない。公開は「公開する」を押したときだけ。自動生成の候補は、人が保存するまで一覧に入らない。

| 項目 | 結果 |
|---|---|
| ユニットテスト | 231 件すべて通過（追加 82 件） |
| E2E | 29 件すべて通過（スタジオ 5 件を追加） |
| ESLint・型チェック | エラー 0 |
| サンプル「緑シルエットの上下セット」 | 警告なし。合い具合 0.78。緑の消し残り 0.2% 未満 |
| サンプル「緑シルエットのドレス」 | 警告なし。合い具合 0.74。スカートの白いハイライトに穴なし |
| サンプル「黒シルエットに紺のスカート」 | 「色が近い」の警告あり（ひだが欠ける。設計書 4 章のとおり） |

| 1 枚の処理時間 | 約 2 秒（2000×2000 の画像、開発環境） |
| ゲーム本体の JS | 527.8 KB（変更なし。React が別ファイルに分かれただけ）。スタジオは 28.6 KB で、開いたときだけ読み込む。PWA の事前キャッシュには入らない |

設計書 4 章の「残った粗」のうち、ふちの緑と首飾りの内側の白は解消した。残っているもの: 細いふち飾り（幅が数 px）の外側に、ごく薄い緑が残る箇所がある。半透明の布（チュール）ごしにシルエットの色が透けて描かれた部分は、色が残る。どちらも消しゴムで直せる。

## 4. 確かめられていないこと

1. **Gemini API を実際に呼んでいない**（この開発環境にキーが無く、公式の説明のページも開けなかった）。`tools/studio/ai.ts` の Gemini の呼び出し方とモデル名（`gemini-2.5-flash-image`）は、記憶にもとづいて書いたもの。最初に動かすとき、エラーが出たらここを直す。
2. **Claude API も実際には呼んでいない**。SDK の型には合っているが、返答の内容（品目の案の質、検品の厳しさ）は未確認。
3. **合格率が分からない**。Gemini がシルエットをどの程度守るか、絵柄がどの程度揃うかは、最初の試行（1 体のドールで 10〜20 点）で測る。結果で、作り直しの回数や部分拡大の要否を決める。
4. 体の部位の推定は、今の 2 体（腕を体から離して立つ姿）でしか確かめていない。違うポーズのドールでは、画面で直す必要がある。
5. シルエット色の検出は、ドールの形を手がかりにしている。体にぴったり沿う単色の服（全身タイツなど）では、服をシルエットと取り違えることがある（警告が出るか、服が消える）。自動生成では指定した色を使うので起きない。
6. iPad では確かめていない（スタジオは PC 用。ゲーム本体は変更していない）。

## 5. 作者に頼むこと

1. PC で `DressUpGame` と `DressUpGame-content` を同じ階層に置き、`npm ci` のあと `npm run studio`。
2. 手持ちの AI 画像を数枚入れて、切り抜きと位置合わせの出来を見る。1 点保存して「ゲームで確認」。
3. 「公開」で iPad に届くことを確かめる。
4. Claude API キー（Claude Console）と Gemini API キー（Google AI Studio）を PC の環境変数に置き、各サービスの管理画面でも金額の上限を設定する。
5. 「ドールと型紙」で絵柄の説明と見本を入れ、「テーマから作る」で 10〜20 点を作り、何点が「合格」「注意あり」「失敗」になったかを教えてもらう。
