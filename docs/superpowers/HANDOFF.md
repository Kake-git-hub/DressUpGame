## 2. 次にやること: スタジオ（段階 2 と 3 を統合）

`docs/superpowers/plans/2026-11-16-stage2-asset-studio.md` は **PC 専用・手動生成の前提で書いた旧計画**。その後、作者の決定で前提が変わったので、**そのまま実行しない**。作業 1〜4（画像処理の純粋関数、位置合わせ、1 枚の処理、一覧ファイルの編集）は、新しい前提でもほぼそのまま使える。

### 作者が決めたこと（2026-11-16）

1. **スタジオはアプリに組み込む**。ゲームとは別ページにして、開いたときだけ読み込む（遊ぶ側を重くしない）。
2. **ドールを起点にする**。ドール（透過 PNG）をアップロード → スタジオが型紙（シルエット、体の部位の位置）を作る → 以後の生成は、すべてその型紙のシルエットを AI に渡して行う。アイテムごとにポーズがずれないようにするため。
3. **テーマからの自動生成を含める**。文章（品目の企画、検品）は Claude API、画像は Gemini API。
4. **背景の生成も含める**。
5. **利用者はキーを入力しない**。API キーはサーバー側に置き、金額の上限もサーバー側で管理する。
6. **将来は一般公開し、スタジオを有料機能にしたい**。
7. **スタジオの開発は、PC 上で先に進めてよい**（デバッグしやすい方を選んでよい）。
8. シルエットと背景の色は固定しない。服の予定色から、いちばん切り抜きやすい色を自動で選ぶ（設計書 10 章 1）。
9. 公開の前に、必ず人が候補を見て採用・不採用を選ぶ（自動公開はしない）。

### 私の提案（未承認。次のセッションで作者に確認する）

5 と 6 により、**サーバーが必要**になる（ブラウザだけではキーを隠せない）。次の形を勧める。

- **スタジオを「画面」と「API」に分ける**。画面は API を呼ぶだけにする。
- **まず PC 上で API を動かす**（Node。キーは PC の環境変数。素材フォルダに直接書き、公開は git）。旧計画の作業 5 の API がこれに当たる。開発とデバッグが最も速い。
- **同じ API を、あとでサーバーに載せる**（利用者の認証、利用量の上限、課金は、その時点で足す）。画面はそのまま使える。
- **画面は最初からアプリの別ページとして作る**（開発中は PC の API に、公開後はサーバーの API につなぐ）。

### 次のセッションで作者に確認すること

1. 上の「PC で API を先に作り、あとでサーバーに載せる」進め方でよいか。
2. サーバーをどこに置くか（例: Cloudflare Workers、Vercel など）。無料枠・運用の手間・画像処理（sharp が使えるか）で選ぶ。未調査。
3. 有料化の範囲: 利用者ごとに素材を分けるのか（各自のドールと服）、全員が同じ素材を見るのか。ログインの方法、課金の方法。これは大きな設計なので、**スタジオが PC で動いてから**、別の設計書として扱うのがよい。
4. Claude API キーと Gemini API キーの用意（PC の環境変数に置く。リポジトリには入れない）。金額の上限は、まず各サービスの管理画面で設定してもらう。
5. `tools/studio/fixtures/` に入れたサンプル画像 3 枚（作者提供）を、公開リポジトリに置いたままでよいか。

### 確かめられていないこと

- Gemini の画像生成 API が、添付したシルエットをどの程度守るか、絵柄がどの程度揃うか。**最初に 1 体のドールで 10〜20 点を生成し、合格率を測る**（設計書 7.7）。結果で、部分拡大の要否や作り直し回数を決める。
- 位置合わせと切り抜きは、捨てる前提の Python の試作で確認しただけ（設計書 4 章）。緑シルエットの 2 枚は良好、黒シルエット＋紺のスカートは欠けた。TypeScript の実装はまだ無い。
- モデル名や API の形は変わりやすい。Claude API を書くときは `claude-api` スキルを読み、Gemini は公式の説明を確認してから書く。

## 3. コードの地図

| 場所 | 役割 |
|---|---|
| `src/App.tsx` | 画面全体と状態。素材の読み込み、服装の復元と保存、先読み |
| `src/content/` | 一覧ファイルの型と検証（`manifest.ts`）、読み込み（`loadContent.ts`）、起動時の状態（`startState.ts`）、先読み（`prefetch.ts`）、旧データの削除（`legacyCleanup.ts`） |
| `src/pipeline/` | 画像処理の純粋関数: 外接矩形（`alpha.ts`）、縁からの背景除去（`removeBackground.ts`）、右下の小片除去（`removeCornerSpeck.ts`）、色相（`hue.ts`）。スタジオの切り抜き・位置合わせもここに足す |
| `src/engine/PixiEngine.ts`、`src/components/AvatarCanvas.tsx` | 描画（PixiJS）。切り抜き画像は、元キャンバスの中心を原点にして描く |
| `src/components/ItemAdjustPanel.tsx`、`HueCanvas.tsx` | 調整モード。プレビューは CSS で重ねている（描画と二重実装。「描画」の段階で一本化する予定） |
| `src/services/outfitStorage.ts`、`stateStorage.ts` | 端末に保存する小さな状態 |
| `tools/content/buildContent.ts` | プリセットのフォルダ → 配信用の一覧と画像。`npm run content:migrate -- <入力> <出力>` |
| `e2e/` | E2E。`e2e/globalSetup.ts` がテスト用の素材を `dist/e2e-content` に作り、アプリを `?content=e2e-content/` で開く |

残っている段階（ロードマップ参照）: スタジオ（2＋3）→ 描画の Canvas 2D 置き換え（計画あり: `2026-11-16-stage-render-canvas2d.md`。JS の大半を占める PixiJS を外す）→ 操作の改善（タップで着脱、一覧のスクロール、調整対象の選択）→ 説明書の統合。

## 4. 作業の決まり（このプロジェクトで続けてきたやり方）

- **作者への報告は日本語**。専門用語を避け、数値と「確かめられていないこと」を必ず書く。
- **段階ごとに計画を書き、作者の了承を得てから実装する**。実装はセッション内で順に行い、最後に別の目（サブエージェント）の全体レビューを 1 回かける。
- **テストを先に書く**。失敗を見てから実装する。
- **`main` への push は、作者が「マージして」と言ったときだけ**。`main` に入ると GitHub Actions が自動で公開する。ふだんは作業ブランチに push する。
- **push 済みのコミットは書き換えない**（force push は拒否される）。
- 版数は `src/App.tsx` の `APP_VERSION` と `README.md` の両方を上げる。
- iPad 実機でしか確かめられないことは、確認項目として作者に渡す。
